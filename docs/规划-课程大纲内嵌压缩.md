# 规划：全部内容内嵌 + 算法层无损压缩（2026-11-17）

> 决策前提（主人 2026-11-17）：**不搞下载，全部嵌进 App**；大纲与培养方案都走「技术/算法层面压缩」，**内容不丢**。
> 本文只写「怎么做到、每步省多少、怎么证明没丢」。所有数字都在真实产物上跑出来，脚本在 `在途/curriculum/_work/`。

## 0. 口径（先定死，后面所有取舍都按它）

| 项 | 定死 |
|---|---|
| 无损的定义 | 从压缩资产还原出的对象，**与源 JSON 逐字段相等**（含字符串原样、顺序、空值）。用 2066 + 168 份全量 round-trip 单测锁住，不靠人眼 |
| 允许做的事 | 换更強的压缩算法；改变存储布局；把「可由其它字段机械重建」的重复内容改成重建（必须 100% 可逆，且重建函数进单测） |
| 不允许做的事 | 删内容、四舍五入、把长文截断、用「相近字段」冒充、把「暂缺」填成 0 |
| 交付形态 | 全离线。首次打开任何课程/方案都不需要网络 |
| 体积目标 | 在“内容全部保留”前提下把 assets 压到最小；APK 变大是接受的代价，但每 0.1 MB 都要有实测依据 |

## 1. 压缩算法选型（同一份 35.02 MB 语料实测）

| 算法 | 逐包合计 | 单流全语料 | 编码耗时 | 解码内存 |
|---|---|---|---|---|
| gzip -9（=现在 AAPT 的做法） | 7.46 MB | 7.45 MB | 1.3 s | 32 KB |
| **brotli q11 lgwin22** | **4.27 MB** | ~4.0 MB | 52 s（一次性，构建期） | 2^22 = 4 MB |
| xz / LZMA2 dict4M | 4.37 MB | 4.15 MB | 10 s | 4 MB |
| xz / LZMA2 dict8M | 4.37 MB | 4.08 MB | 9 s | 8 MB |
| xz / LZMA2 dict16M | 4.37 MB | 4.03 MB | 10 s | 16 MB |

**结论：brotli q11**。它比 gzip 小 **43%**，还比 xz 略小、编码更快。

为什么 gzip 差这么多：deflate 只有 32 KB 窗口，看不到「同一个学院里第 30 门课和第 800 门课用同一条教材」；brotli 窗口 4 MB 就能看到整个学院，并且自带文本静态字典（对 UTF-8 中文与 JSON 键名都有加成）。

> 窗口大小的取舍见 §2.5（解码端要按窗口大小占内存，这是端上唯一硬指标）。

## 2. 压缩前的四件事：结构化无损重塑

压缩只是最后一步。真正决定体积的是「塞给压缩器的字节长什么样」。

### 2.1 大包化（大纲）：2066 个文件 → 14 个包

现在每门课一个 17 KB 的文件，AAPT 逐文件压，字典跨不了文件 → 10.96 MB。
合成「一行一门课」的 14 个学院包后 → 7.46 MB（gzip）/ 4.27 MB（brotli）。**纯白拿。**

### 2.2 索引导出（大纲）：把「在哪」和「是什么」分开

`plans` 与 `syllabus` 各有一个索引，只存可检索字段：

- 大纲索引：2066 条 `{code,name,credit,hours,type,college,pack,line}` → 紧凑 0.38 MB → **brotli 后 0.035 MB**
- 有了它，「这门课有没有大纲 / 叫什么 / 几个学分」全部不用解包。

### 2.3 课程行抽池（培养方案）：17232 → 5574

培养方案 62% 的体积在 `课程设置与教学进程`，而 **17232 行里只有 5574 个不同文本**（公共课、学科基础课在几十份方案里逐字重复）。抽池后：

| 形态 | gzip | brotli |
|---|---|---|
| 现状：168 份各自压 | 1.163 MB | — |
| 抽池 + 3 个年包 | 0.570 MB | **0.345 MB** |

### 2.4 可重建段（大纲）：实测后**不做**

`一、课程基本信息` 就是把 `基本信息` 字段按「键 + 值」逐行拼出来的文本 —— 2134 门里 1481 门可精确重建（1470 完全一致 + 11 字符集等价），653 门因抽取断行差异不可精确重建。

**但实测收益只有 2.0%（0.079 MB）**：brotli 早就把「一、」和「基本信息」之间的重复吃掉了（两者在同一流里）。为了 79 KB 去做「逐门判断可否重建 + 标记位 + 重建函数 + 全量比对」，不划算。

> 同理测了其它字段的压缩贡献，结论一致：结构化字段都近乎「免费」。
> | 删掉 | 省 | 说明 |
> |---|---|---|
> | 全部 `章节` | **83.5%** | 真正的正文都在这里 |
> | `六、教学内容` 一节 | **31.3%** | 最大一块真内容 |
> | `七、`（考核方式等） | 17.8% | 第二块 |
> | `二、`（课程简介） | 11.8% | 第三块 |
> | `教学内容学时一览表` 整个字段 | 2.2% | 与 `六、` 高度重复，已被压缩器吃掉 |
> | `基本信息` 整个字段 | 1.8% | 与 `一、` 重复 |
> | `教学章节` 整个字段 | 2.2% | 与 `六、` 重复 |

### 2.5 窗口大小：选 lgwin 22（4 MB），不选 24

brotli 解码器的 ring buffer = 2^lgwin 字节，这是端上唯一硬指标。14 个包实测：

| lgwin | 解码窗口 | q9 | q11 |
|---|---|---|---|
| 18 | 0.25 MB | 5.28 MB | 4.78 MB |
| 20 | 1 MB | 4.85 MB | 4.36 MB |
| 21 | 2 MB | 4.80 MB | 4.28 MB |
| **22** | **4 MB** | 4.79 MB | **4.27 MB** |
| 24 | 16 MB | 4.79 MB | 4.27 MB |

**结论：q11 + lgwin 22**。比 lgwin 24 只差 0.00–0.01 MB，解码内存从 16 MB 砍到 4 MB。q9 相比 q11 要多付 0.5 MB，不值。

## 3. 体积预算（实测，不是估算）

| 形态 | 大纲 | 培养方案 | 索引/META | assets | APK |
|---|---|---|---|---|---|
| **现在**（只有土环） | 0.89 MB（167 门，逐文件 gzip） | 1.16 MB（168 份，逐文件 gzip） | 0.01 MB | 2.17 MB | 5.16 MB |
| 若不做任何事、直接塞 2066 门 | 10.96 MB | 1.16 MB | 0.41 MB | ≈12.6 MB | ≈15.6 MB |
| 只换压缩器（文件数不变） | ≈8.2 MB | 0.345 MB | 0.035 MB | ≈8.6 MB | ≈11.6 MB |
| **本规划**（大包化 + 抽池 + brotli q11 lgwin22） | **4.296 MB**（包 4.268 + 索引 0.028） | **0.346 MB**（池 0.068 + 3 年包 0.277 + 索引 0.002） | 含在上面 | **4.642 MB** | **≈7.66 MB** |
| 加「可重建段」 | 4.22 MB（−79 KB） | — | — | — | 不做，见 §2.4 |

读法：**内容从 167 门变 2066 门（12.4 倍）、从“没有培养方案”到 168 份全内嵌，APK 从 5.16 MB 只涨到 ~7.7 MB（1.5 倍）**。
对比「什么都不做」的 15.6 MB，本规划省下 **7.9 MB**（51%）。
外加解压库 `org.brotli:dec`（纯 Java，jar 约 150 KB，进包后压得更小）。

## 4. 端上设计

### 4.1 资产布局（改造后）

```
assets/curriculum/
  META.json
  plans/
    index.json        年份 → [{id, major, type, line}]
    pool.json         5574 条课程行       1.48 MB 明文 / 0.068 MB br
    2023.jsonl.br     55 份方案           0.088 MB
    2024.jsonl.br     67 份方案           0.085 MB
    2025.jsonl.br     46 份方案           0.104 MB
  syllabus/
    index.json        2066 条             0.035 MB br
    农学院.jsonl.br     196 门              0.4x MB
    ... 共 14 个
```

### 4.2 读取路径

- **培养方案**：进页面 → 读 `plans/index.json`（约 20 KB，缓存内存）→ 用户选某专业 → 解当年那个 `.br`（最大 1.10 MB 明文，耗时 ~100 ms）→ 第 N 行取方案 → 用 `pool.json` 展开课程行 → 渲染。
- **大纲**：点某门课 → 读 `syllabus/index.json` 找 `{pack, line}` → 解该学院包（最大 3.76 MB 明文）→ 扫到第 line 行 → 解析。
- **缓存策略**：解出来的明文放内存 LRU，上限 1 个学院（3.76 MB）+ 1 个学年（1.10 MB）；切换就失效，不做磁盘缓存（assets 本来就在本地，磁盘缓存是重复存储）。

### 4.3 依赖与构建

- 解压库：`org.brotli:dec`（纯 Java，无 native，不新增 ABI 体积）；构建期用 Python `brotli` 或 CLI `brotli -q 11` 生成 `.br`。
- `build.gradle`：`androidResources { noCompress += listOf("br") }` —— 否则 AAPT 会再 deflate 一遍（对随机数据无收益，白白多一次解压）。
- 构建脚本：`在途/curriculum/_work/pack.py`（大纲）+ 新增 `pack_plans.py`（培养方案），产物直接落到 `app/src/main/assets/curriculum/`。

## 5. 验收（缺一不可）

1. **无损 round-trip**：2066 门大纲 + 168 份方案，从 `.br` 资产走「端上同一套解析路径」还原，与源 JSON **逐字段 `assertEquals`**。JVM 单测，不靠人眼。
2. **体积**：`build-release.bat` 出的 APK 与 §3 预算对齐（超出 0.2 MB 要写原因）。
3. **冷启动时延**：真机（vivo V2301A）从点开课程到出正文 < 300 ms（含解压）；培养方案 < 400 ms。
4. **内存**：解析峰值 < 24 MB（`DebugLog` 记录，加断言）。
5. **离线**：飞行模式下全部可读。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| brotli 纯 Java 解码慢于 C 实现 | 实测 lgwin/q 组合；必要时把包切小（按学院已够小）；有 `DebugLog` 计时 |
| 低端机内存不够（lgwin 16 MB） | 降 lgwin 到 20–22，用体积换内存，见 §2.5 实测 |
| 构建期 brotli 编码慢（全量 52 s） | 只在资产变化时重跑；产物入库缓存，增量构建不受影响 |
| 「可重建段」重建出错 → 内容错 | 只在 100% 精确匹配时启用；单测逐门比对全量 |
| APK 变大触发分发顾虑 | 仍是个人测试构建；分发需学校授权（既有口径不变） |

## 7. 落地顺序（每步都能独立验收）

1. ~~修解析缺陷~~ **（已查清，结论与预想不同，见 §8）**
2. **出资产**：`syllabus/<学院>.jsonl.br` + `syllabus/index.json.br`；`plans/pool.json.br` + 3 个年包 `.br` + `plans/index.json.br`。→ `在途/curriculum/_work/build_assets.py`（一条命令出全部资产并自验）
3. **改读法**：`CurriculumAssets.kt` —— 索引走小文件，正文走「解包 → 扫行」，加内存 LRU（1 学院 + 1 学年）；解压封装成一个 `unbrotli(ByteArray)`。
4. **锁无损**：JVM 单测把 2066 + 168 份全量 round-trip 与源 JSON 做逐字段 assertEquals；另加「索引条数与包行数一致」的断言。
5. **量体积**：`build-release.bat` 出包，与 5.16 MB 基线和 §3 预算对表；超 0.2 MB 写原因。
6. **真机验收**：点开课程计时、飞行模式通读、内存峰值记录（`DebugLog`）。

> 关于「单流 3.94 MB」：能再省 0.33 MB，但要 16 MB 解码窗口且必须一次解全部，低端机风险大于收益，**不做**。

## 8. 进度（2026-11-17）

### 8.1 第 1 步「解析缺陷」查清了，但结论相反

原先记的是「公共课教学单位课程代码字段粘连是解析缺陷」。逐条看原始值后确认：**这是 PDF 原文就一格四码**，不是解析错。

```
'902031101、902031102、\n902031103、902031104'  → 体育（篮球/健美操/滑冰…）四个学期共用一份大纲
'90203110、902031102、\n902031103、902031104'   → 橄榄球那份原文就少一位（PDF 里的笔误）
```

按「数据诚实」口径处理：`课程代码` **原样保留**（PDF 写什么就是什么，含换行和那个少一位的笔误），另加派生字段 `课程代码列表`（按 `、,，;；空白` 拆开）。共 21 条多码课程加了该字段，源 JSON 已写回。索引里用首个代码做 `id`，同码多门（体育）再加课程名区分。
