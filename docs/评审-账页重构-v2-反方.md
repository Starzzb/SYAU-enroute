## 1. 可读性论证是否成立

### 1.1 「正文 15/24 = 1.60」论证攻击的是幽灵，不是现状渲染值
- **问题**：§3.2 说「现状 body 是 1.43–1.46，低于下限，取 1.60 是带内中点偏上；15sp 比 16sp 每屏多约一行」。但 1.43–1.46 是 `EditorialTypography` 里**零消费的死 token**（审计已证 `MaterialTheme.typography` 引用 0 处）；真正渲染的资讯详情正文是 `FeedScreen.kt:1647` 硬编码的 **14sp/25sp = 1.79×**，审计 §0 判定它 ✅ 落在 1.5–1.8。把正文改成 15sp/24sp = 1.60，行高倍数反而从 1.79 降到 1.60，且 14→15sp 每屏行数**减少**——「保住信息密度」的论据和数字对不上，实际是「改了没变好」。
- **证据**：v2 L92–93；审计 L11–17（1.79 ✅）、L40–42（死 token 1.43/1.44/1.46）、L67（`bodyLeading=1.45` 零消费）；`FeedScreen.kt:1647`。
- **建议**：以**渲染值**为基线重写 §3.2。若正文维持 14sp，行高只提段间距（审计 S1 的修法），别动字号；若要动字号，明确「14→15sp 每屏少 N 行」的真实代价，并承认行高倍数从 1.79 回退到 1.60。
- **严重度**：应改。

### 1.2 gridCell 下限在 41.9dp 文本宽下没有兜底，等于用「信息完整」换「字号合规」
- **问题**：§3.3 承认「10sp 下限与课名+教室+教师三行不可兼得」，两行制在 41.9dp 文本宽 ≈ 4 字/行，「放不下就省略号，接受只显示课名」。这是把主网格的信息量砍到只剩课名，且把风险全推到「待真机实测」——但没有「实测仍挤」时的用户侧兜底（如长按直达详情、省略号态至少保留教室）。
- **证据**：v2 L105–108；审计 L186（课程格 ≈4.2 字/行）、L243（3 行塞 10/8/7.5sp 仍放不下 6 字课名）。
- **建议**：给省略号态定一个可见的次级信息（例：课名 + 一个可点的「·」徽标进详情），把「完整信息进 CourseDetail」写成明确交互，而不是只写「接受省略号」。
- **严重度**：可选。

## 2. 形状统一能否真强制

### 2.1 CI「最终裁决」测试 B 大面积漏检，禁裸值可被字面量变形绕过
- **问题**：§2.2 的检查 B 正则 `\b\d+(\.\d+)?\.dp` 且只在 `RoundedCornerShape(...)` 内匹配。以下全部绕过 B（而 B 被定为「最终裁决」，A 只是本地快查）：
  - `CircleShape`（`HomeCards.kt:113`、`FeedScreen.kt:353/979/1130`、`TimetableScreen.kt:1267`）——B 根本不查；
  - `cutCorner(8.dp)`——B 只认 `RoundedCornerShape`；
  - `RoundedCornerShape(50)`（Int percent 重载，无 `.dp`）；
  - `13f.dp`——`\d+` 后是 `f` 不是 `.`，不匹配；`val x = 13; x.dp` 同样绕过。
- **证据**：v2 L66–69；`RoundedCornerShape`/`CircleShape` 实际调用点见 grep（`FeedScreen.kt:631/904/938/940/1063`、`HomeCards.kt:113`、`TimetableScreen.kt:920/1267` 等）。
- **建议**：弃用文本正则，改用 **detekt `ForbiddenImport`**：在非 `ui/theme` 包禁止 import `androidx.compose.ui.unit.dp|sp`、`androidx.compose.foundation.shape.RoundedCornerShape|CircleShape`（import 级检查，字面量变形绕不过）；同时只向业务层暴露语义 `Shape` / `Dp` 对象（`Form.current.shapes.card`），不让业务代码碰到原始 `Dp`/`sp` 构造函数。测试 B 若要保留，至少补上 CircleShape、cutCorner、percent 重载、别名 import 四个用例。
- **严重度**：阻断。

### 2.2 gate 只扫 `ui/`，整块 `widget/` 包与 token 文件被豁免
- **问题**：§2.2/§3.4/§4.4 的扫描路径全部是 `...\ui`（非 theme）。`cn.dkarbon.enroute.widget.TodayWidget.kt` 不在 `ui/` 下，其 `.dp` 间距（1/2/4/6/8/12/38）与字号裸值（审计 L1101–1107）完全不在 gate 内——这是另一块用户可见界面。此外 `ui/timetable/TimetableTokens.kt` import 了 `CircleShape/RoundedCornerShape`（L16–17），PowerShell 检查 A 用 `Select-String` 原文匹配会把**import 行**也当违规，产生无法区分的误报。
- **证据**：v2 L60、L113、L152（路径都锚在 `ui`）；`widget/TodayWidget.kt:26/126–167`；审计 L1101–1107；`TimetableTokens.kt:16–17`。
- **建议**：gate 覆盖整个 `cn.dkarbon.enroute` 源树（widget 也是 UI 出口）；给 `TimetableTokens.kt` 一个明确归宿（并入 `ui/theme` 或显式声明为 token 包白名单）；检查 A 锚定到调用语法而非 import 行。
- **严重度**：阻断。

### 2.3 `pillSize` 被写成「999 整圆」，与代码的「直径 20dp」是两个量纲
- **问题**：§2.1 表格把 `pillSize` 标为「胶囊、头像、轴牌（已有字段，直径）999/999 整圆」。但代码里 `FormSpec.pillSize = 20.dp`（Hard 与 Ledger 都是），且消费点是 `LedgerTimetable.kt:224–225` 的 `height(f.pillSize)` + `clip(RoundedCornerShape(f.pillSize / 2))`——它是**直径**。照规范改成 999，节次圆牌直径变成 999dp，课表直接爆掉；同时 999 是「圆角半径」概念，和「直径」被并进了同一档。
- **证据**：v2 L44；`EditorialTokens.kt:284/314`；`LedgerTimetable.kt:224–225`；审计 L24（`FormSpec.pillSize = 20`）、L44（`f.pillSize/2`）。
- **建议**：`pillSize` 保持直径 20dp 不动；「整圆」单独成档（如 `radiusPill` 语义档，或直接暴露整圆 `Shape` 对象）。批 1 的「HARD 逐像素不变」验收也会因 pillSize=999 被直接打破。
- **严重度**：阻断。

## 3. 重启方案的真实代价

### 3.1 「立即重启」的进程自杀顺序自相矛盾，且没规定同步落盘
- **问题**：§8.1.3 写 `startActivity(launchIntent) + finishAffinity() + Process.killProcess(Process.myPid())`。`startActivity` 启动的新 Activity 和当前代码在**同一进程**里，紧接着 `killProcess` 会把刚启动的 Activity 连同进程一起杀掉——重启大概率不落地（进程死亡即任务消失，除非 launcher 重起，而 spec 没保证）。同时没写 `launchIntent` 的 component/flags（须 `NEW_TASK|CLEAR_TASK` 指向 launcher Activity），也没要求设置仓库用 `commit()` 同步落盘——若用 `apply()`（异步）后立即 kill，主题保存可能丢失。
- **证据**：v2 L259–260；`MainActivity.kt:33`（onCreate 纪律：只做 super/enableEdgeToEdge/setContent）。
- **建议**：要么「`startActivity(launchIntent)` → `finish()`」只重建 Activity 不杀进程；要么按 Android 官方最小重启范式（写盘用 `commit()` 确认返回后再触发重建，`launchIntent = packageManager.getLaunchIntentForPackage(...)` 并补 flags），不要 `killProcess` 跟在 startActivity 后面。
- **严重度**：阻断。

### 3.2 「避免全量 recompose」的论据站不住——热切链路现在就是活的
- **问题**：§8.3 说热切等于整棵树重组、中端机掉帧，所以要杀进程。但现状 `MainActivity.kt:138–145` 已经把 `themeMode/styleSet/colorSource/customPalette` 四个值从 `ui` StateFlow 经 `collectAsStateWithLifecycle` 喂给 `EnRouteTheme`——主题切换本来就是一条已工作的状态流；把 typography/shapes/FormSpec 也纳入同一入参（它们已经是 `EnRouteTheme` 的参数），热切只是一次普通 recompose。对一个「每天开十几次」的 App，杀进程重启的代价是丢导航栈、丢滚动位置、丢未保存输入，比一次 recompose 贵得多。
- **证据**：v2 L271–276；`MainActivity.kt:138–145`；`Theme.kt:190–201`（EnRouteTheme 已接受全部四个入参并纯函数化）。
- **建议**：折中方案——保留 §8.1.4 的纯函数（`baseTokenSet/FormSpec.of/PaletteGate`），但用 `key(themeFingerprint)` 重建 Composition 或让 EnRouteTheme 参数进 state，**只重建组合层、不重启进程**；把「杀进程」降级为兜底，而不是默认路径。
- **严重度**：应改。

## 4. 批次划分是否可编译、可验收

### 4.1 批 1 的 `SpaceTokenTest` 按定义必然失败；线宽这一整类审计发现被丢弃
- **问题**：§4.4 说「提取所有 `.dp` 数字，断言 ∈ 4.1 允许集」。但仓库里有 28 处**线宽裸值**（0.75/0.8/1/1.5/2 dp，审计 §4）以及 `cellInset=3.dp`、`shadowRadius=6.dp`、`width(3.dp)` 等非间距 `.dp`，全都不在 `{0,2,4,8,12,16,20,24,32,44,48,56,80}` 里——测试必红，批 1「两个测试绿」验收不可达。更根本的是：审计把「线宽」列为第 4 类 token 问题（28 行裸值，`0.75dp` 低于 hairline），v2 全文**没有任何 Stroke 线宽的收敛方案**，这一类问题被整段丢掉。
- **证据**：v2 L123、L152–153；审计 L1109–1144（线宽裸值表）、L1113（取值全集 `0/0.75/0.8/1/1.5/2`）；`ErodedCard.kt:59`（0.75.dp）、`LedgerTimetable.kt:83`（1.5.dp）。
- **建议**：把 `SpaceTokenTest` 范围明确限定为 `padding/Spacer/size` 参数（或白名单排除线宽/形态）；另立 `StrokeTokenTest` 管 `0.75/0.8/1/1.5/2`，并把 0.75dp 这类「低于 hairline」的散值收敛到 `Stroke` 档。允许集与测试口径先对齐再谈批 1。
- **严重度**：阻断。

### 4.2 允许集自相矛盾：`rowTall = 64dp` 不在 §4.1 允许集里
- **问题**：§4.1 的取值集不含 64，§4.2 却新增 `rowTall = 64dp`，§4.4 又断言所有 `.dp` ∈ §4.1 允许集——`rowTall` 连自己批次的测试都过不了。
- **证据**：v2 L123（允许集）、L141（rowTall 64dp）、L152–153（断言 ∈ 4.1）。
- **建议**：把 64 补进 §4.1 允许集，或把「新增 token 先于测试」的依赖顺序写进批 1 的验收。
- **严重度**：阻断（并入 4.1 一起改）。

### 4.3 批 1 删阴影、批 4 才补层级，中间三个批次账页处于半成品
- **问题**：批 1 把 `FormSpec.Ledger.cardShadow=false`（v2 L283），LEDGER 软阴影立即消失；替代它的 L1–L3 层级规则（§6）却排到批 4（v2 L301–303）。批 2、3 若按「真机验收」跑，账页是「没阴影、没新层级」的中间态。且 §6 又重复写了一遍「FormSpec.cardShadow 账页改 false」，同一改动出现在两个批次。
- **证据**：v2 L283（批 1）、L214（§6 重复）、L301–303（批 4）。
- **建议**：把 `cardShadow=false` 与 §6 层级规则合并进同一批（或允许 cardFloat 保留到批 4 再删），消除跨批的视觉回归窗口；删掉 §6 与批 1 的重复表述。
- **严重度**：应改。

### 4.4 批 2 的「748 行分批清」与「grep 归 0」验收互相矛盾，白名单机制未定义
- **问题**：批 2 验收要求「`ui/` 非 theme 目录 grep `fontSize` 裸值归 0」，但同节又说「白名单逐文件清，748 行分批」——要么本批真清完 748 行（工作量与回归风险巨大），要么 CI 测试在批 2 期间一直红，「每批可独立 compile-check + 测试绿」不成立。白名单清单、每批清空范围都没有定义。
- **证据**：v2 L289–293。
- **建议**：给出白名单文件清单与每批清空的目标行数；或把「grep 归 0」降为批 2 的**最终**验收、批内以 compile-check + 增量绿为准。
- **严重度**：应改。

## 5. 与既有约束冲突（AGENTS.md / 票 25 CustomPalette）

### 5.1 七对闸门会误伤现有预设，「扩为七对」不是纯增量
- **问题**：§5.2 说现有五对「扩为七对」，新增「主色/cardAlt ≥4.5」。但预设色板从没按 cardAlt 重算过：浅色主色预设「麦秆黄（深）`#8F6713`」对纸底只有 **4.56:1**（贴线），对更暗的 `cardAlt`（HARD `#EDE8DF` / LEDGER `#F1ECE1`）大概率跌破 4.5——保存时被新闸门拒绝，与票 25「预设开箱即达标」和 §5.2「预设+微调」矛盾。
- **证据**：v2 L178–181；`CustomPalette.kt:190–199`（8 档浅色主色，麦秆黄（深）注释 4.56:1）、L322–328（现五对）。
- **建议**：落地前先跑 8×2 预设 × `cardAlt` 的对比度矩阵；若贴线预设被卡，要么调预设（换更深一档），要么把「主色/cardAlt」按实际用途定门槛（主色在 cardAlt 上只做 2–3dp 色条，按图形 3:1 即可，§6 L3 自己也是这么说的）。
- **严重度**：应改。

### 5.2 壁纸路径与七对闸门口径不一致：inkVariant 不管 cardAlt
- **问题**：§5.2 给自定义上了七对闸门（含 cardAlt），但壁纸路径的 `PaletteGate.inkVariant` 只推到「paper 与 card 两底 ≥4.5」（`CustomPalette.kt:346–347`），账页的 `cardAlt`/`bandTint` 不入补偿。于是「主色当文字」出现两套下限：自定义管三底、壁纸管两底。
- **证据**：v2 L182–183；`CustomPalette.kt:345–364`。
- **建议**：`inkVariant` 的终止条件与七对闸门对齐（把 cardAlt 加进判定），或在规范里明确「主色永不当文字出现在 cardAlt 上」并据此把七对减回五对。
- **严重度**：应改。

### 5.3 与 AGENTS.md 的兼容性结论（正面确认 + 三处文档漂移）
- **确认不冲突**：§7.3「设置搜索只匹配标题，不匹配说明」与「按钮不自带说明书」一致；§8.2 文案「主题已保存，重启后生效」（10 字）合规；§5.2「ink/inkSoft/inkFaint/rule/brick/olive/amber 永远不动」与「数据诚实」的语义色不动一致；§7.3「本地列表、不进网络」与「只读教务」一致。
- **但有三处文档漂移**：① §5.1「大字标题 — ✅」没写数字，违反规范自己 L7「每个数字都写理由」；② §6 L212 说「EditorialTokens 里两处 feed」——cardFloat 调用点是 `FeedScreen.kt:912/1069`，不是 EditorialTokens；③ §2.1 L48 说「13.dp 不再作为圆角」，审计圆角表里没有 13dp（13dp 只出现在间距 `ContributeSection.kt:288`）。
- **建议**：修掉三处引用；尤其 ②③ 会在批 4 验收时误导 grep。
- **严重度**：可选。
