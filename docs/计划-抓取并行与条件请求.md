## 2. 任务 A：抓取并行化（主收益）

### 现状
`FeedRepository.kt:60` 是串行 `for (src in FeedSources.ALL.filter { it.enabled })`，
14 个源依次抓，每个源内部还有 `extraPages` 的 400ms 间隔（`:67-71`）。
串行意味着总耗时 ≈ 各源耗时之和。

### 改法
用 `coroutineScope` + `async` 并行，**但必须加并发上限**：

```
并发上限 = 4（常量 FEED_FETCH_CONCURRENCY）
```

理由：14 个请求同时打出去在移动网络下会引发 radio 频繁唤醒，反而更慢更耗电；4 是收益与功耗的平衡点。上一个请求结束才启动下一个（`Semaphore` 或 `Channel` 控制）。

### 必须保持的三条不变量（回归测试要覆盖）

1. **单源失败不影响其他源**：每个 `async` 内部的 `runCatching` 语义不变，异常只能落到自己的 `SourceResult`。
2. **结果顺序确定**：`results` 必须按 `FeedSources.ALL` 的原始顺序回填，不能按完成先后。
   实现建议：`results` 用定长数组 + index 写入，或 `awaitAll()` 后按索引重排。
   （现在 `:148-149` 有 `results.clear()/addAll(counted)` 的原地重排，改动后要保证它拿到的仍是同序列表。）
3. **`fetched` 不能是裸 `mutableListOf` 并发写**：`:58` 现在是普通 MutableList。并行下必须改成
   - 每任务返回自己的 `(src, items)`，`awaitAll` 后汇总；或
   - `Collections.synchronizedList` / 独立的 `Channel`。

### 同源内部的额外页：保持 400ms
`:67-71` 的 `delay(400)` 是**同一台服务器**的礼貌间隔，跨源并行不影响它。
也就是说：源与源之间并行，源内部仍串行 + 限速。这是刻意的。

### 预期收益
总耗时从「各源之和」降到「最慢单源 + 排队」。以 14 源、单源 0.3–1.2s 估算，
理论区间见第 5 节；**实际以第 1 步实测为准**。

### 风险点
- **`store.saveBody` 并发**：`FeedStore` 内部有 `mutex`，安全；但注意不要在持锁期间做网络请求（现在没有）。
- **`stateMutex` 只在合并阶段持有**（`:117`），并行抓取阶段不该持锁——改动后要复核这一点没变。
- **取消语义**：`FeedViewModel` 的 refresh 若被取消（切页/重进），所有 `async` 要一起取消。`coroutineScope` 天然满足；不要用 `GlobalScope`。

## 3. 任务 B：条件请求（ETag / Last-Modified）

### 现状
`FeedHttp.get()`（`FeedHttp.kt:24-68`）每次都全量拉。KDoc 第 3 条自己写着
「支持 `ETag` / `Last-Modified` 条件请求（304 能省掉 90% 的轮询成本）—— **目前测试期没接**」。

而且现在 `304` 会被当成失败：`:48-51` 把非 2xx 直接 `return Resp(code, "", current)`，
上层 `:65` 的 `require(first.status in 200..299)` 就抛异常，整源算失败。

### 改法

1. **`FeedHttp.get()` 增加可选入参**：
   ```
   fun get(url: String, timeoutMs: Int = 15_000, cache: HttpCacheEntry? = null): Resp
   ```
   请求时带上 `If-None-Match: <etag>` / `If-Modified-Since: <lastModified>`（存在才带）。
2. **`Resp` 增加字段**：`etag: String?`、`lastModified: String?`、`notModified: Boolean`。
   `304` 时 `notModified = true`，不再走「非 2xx」分支，也**不算失败**。
3. **缓存存储**：新增 `filesDir/feed/http-cache.json`（`FeedStore` 内加读写，沿用其 `mutex`），
   键用 `url`，值 `{etag, lastModified, savedAt}`。不要塞进 `Prefs`（会撑大 SP，且 SP 不适合结构化）。
4. **上层处理 304**（`FeedRepository.kt:60` 起的源任务里）：
   - `notModified` → **跳过解析**，该源记为「未变」，沿用库里已有条目，不产生新增。
   - `SyncReport` 增加 `unchanged: Int`（未变源数量），横幅文案可显示「N 个源未变」。
   - **`require(items.isNotEmpty())` 不能对 304 生效**，否则会把「未变」误判成「解析出 0 条」。
5. **只在列表页用条件请求**。正文（`ensureBody`）是永久缓存 + 按需抓，不参与条件请求。

### 实测注意
- 有些站返回 `ETag` 但没有 `Last-Modified`，反之亦然——两者独立判断，有哪个用哪个，都没有就退化为全量拉（不能因此报错）。
- 校内老系统（`cxcy` 等）可能不支持，返回 200 全量即可，**不要因为「没拿到 ETag」打警告日志**（正常）。
- `304` 响应通常没有 body，`FeedHttp` 的解压/charset 逻辑要能安全跳过。

### 预期收益
轮询（切回前台触发 `refreshIfStale`）时，未改动的源从「下载完整 HTML + 解析」降为「一个 304 往返」，
流量和 CPU 都省。**首次抓取无收益**，收益随使用次数累积。

### 新增单测（JVM，用 `kotlinx-coroutines-test`）

1. **并行不丢结果**：mock 多源、随机完成顺序 → 断言 `results` 数量与顺序都等于源表顺序。
2. **单源异常隔离**：1 个源抛异常，其余仍产出，异常只落到自己的 `SourceResult`。
3. **并发上限生效**：用一个计数器记录同时在飞的请求数，断言峰值 ≤ 4。
4. **304 不算失败**：模拟 `notModified`，断言该源 `unchanged=1`、`failed` 不含它、条目数不减少。
5. **ETag 缺失退化**：没有 etag/lastModified 时不发条件头，正常全量拉。
6. **顺序稳定性**：同一批数据跑两次，合并后顺序一致（防止并行引入不确定排序）。

> 单测不要打真网络。`FeedHttp` 现在是 `object` + 静态方法，测试需要**留一个可注入的取数函数**
> （如 `var fetcher: (String, HttpCacheEntry?) -> Resp = ::realGet`），或者把这层抽成接口再注入。
> 这是本轮唯一的结构性改动，注意别破坏现有调用点（`grep FeedHttp.get` 全部改完）。
