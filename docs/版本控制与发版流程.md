## 2. 版本号规则

`app/build.gradle.kts`：

```kotlin
versionCode = 270          // 必须单调递增，Android 用它判断「是不是更新」
versionName = "0.6.1+m26"  // 展示用；+mNN 是开发批次，见 §2.2
```

发版时两块都要改，**versionCode 只能加不能减**（装低版本会失败：`INSTALL_FAILED_VERSION_DOWNGRADE`）。

## 2.1 两套号：发布版与开发版分开（2026-11-17，主人指令）

原话：「开发版本号的管理也应该另外设置一套约定」。此前发布版和开发版共用一套号，
结果出现两种混乱：同一版本号既有「发过 Release 的包」又有「本机还在改的包」；
批次号（`mNN`）既是里程碑又被当成补丁号用。

从 m27 起分成两条线，**互不占用对方的号**：

| | 发布版 | 开发版 |
|---|---|---|
| 何时用 | 打 tag、发 GitHub Release、能装到别人手机上 | 只在本机／备用机迭代，随时被覆盖 |
| `versionName` | `0.<minor>.<patch>+m<NN>` | `0.<minor>.<patch>-dev.<n>` |
| `versionCode` | `(NN + 1) × 10` | `(NN + 1) × 10 + n`（`n` = 1…9，同批次内自增） |
| 例 | `m26` → 270 | `0.6.1-dev.1` → 271 |
| 标签 | `m26` | 不打标签 |
| 落盘 | 同步 `releases/latest.json`、`CHANGELOG.md` | 什么都不写 |

规矩：

1. **一个批次号只发一次**。`m26` 发出去就是 270，之后同批次的改动一律走 `271…279` 的开发版；
   真要发布就开新批次 `m27` = 280。坏包删 tag 后重发**沿用原号**，不许拿旧号发新内容。
2. **`versionCode` 必须严格递增**，所以开发版的 `+n` 一定大于同批次的发布版，
   装回发布版时要么同号覆盖（`-r`），要么用下一批次 —— 不要为了「干净」把号码调小。
3. **`versionName` 里不写日期、不写功能名**：`+mNN` 已经能对上 `CHANGELOG.md` 的一节。
4. Release 标题格式固定 `m26 · 0.6.1+m26`；说明一句话，详见 `CHANGELOG.md`（AGENTS.md）。

## 2.2 1.0 的门槛（2026-11-17，主人指令）

原话：「在功能完善自洽之前，不要升级到 1.0 版本」。`minor` 可以走（0.6 → 0.7 …），
但 **`1.0.0` 必须同时满足下面全部条件**才允许改：

- [ ] 课表 / 成绩 / 考试 / 资讯 / 地图 / 我的 / 设置 七条主链路都能在**没登录**、
      会话过期、断网、非校园网四种状态下给出正确且不互相矛盾的提示
- [ ] 「暂缺」只出现在真的取不到的地方，没有为了凑数补的假值（数据诚实）
- [ ] 更新链路自己走通：检查 → 下载 → 校验 → 拉起权限 → 装完自动回到前台
- [ ] 没有占位票（`票 NN`）、没有「开发中」字样、没有指向不存在功能的入口
- [ ] 接口诊断 14 条在校园网内全绿；失败时能给出一句真原因
- [ ] 界面里不存在说明书式文字（AGENTS.md「用设计，不用文字」）
- [ ] 至少一台非开发者手机连续使用一周，无崩溃、无数据错乱

不满足就继续留在 `0.x`。这条不设期限。

### ⚠️ 切换签名的代价（一次性）

debug 签名与 release 签名**不同**，所以第一次装 release 包必须**先卸载旧包**
（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）。卸载会清掉本机数据：
课表（可重新同步）、地图标注（**先「导出标注」备份**）、登录态（重新登录一次）。

**建议现在就切**（内测人少、代价最小），之后所有版本都能直接覆盖更新。

### 🔑 密钥备份（必须做）

`enroute-release.jks` 丢了就**永远无法更新已安装的用户**，只能换包名重发。
请离线备份两处（U 盘 + 网盘/密码管理器），密码一并存。

## 4. 怎么发更新包（**服务器不发 APK**）

实测服务器出口带宽只有约 **148 KB/s（≈1.2 Mbps）**：20MB 文件 120 秒没下完。
**所以不走服务器发 APK**（服务器只承担 1KB 级的 `latest.json` 与地图补丁 API）。

| 方案 | 适合 | 说明 |
|---|---|---|
| **A. 网盘 / 直发**（**现用**） | 内测 | release 包仅 **4.74MB**，微信/QQ/网盘都很轻松。发文件或直链 |
| B. 对象存储 OSS | 人多时 | 阿里云 OSS 独立带宽、几块钱/月，速度远好于小带宽 ECS；可给出稳定直链 |
| C. 服务器 `/var/www/app/` | ❌ 不用 | 已配好但**只放 `latest.json`**，不放 APK |
| D. GitHub Releases | 存档 | 国内下载慢且常被墙，只作备份 |

**为什么 release 包小这么多**：`assembleRelease` 走 R8 混淆 + 资源优化，23MB(debug) → **4.74MB**。
这直接把「带宽不够」的问题消掉大半。

发版时服务器只需更新一个极小的文件：

```
/var/www/app/latest.json      # <2KB
{ "versionCode": 20, "versionName": "0.1.0-m20",
  "url": "<网盘直链或 OSS 直链>", "sha256": "…", "size": 4970000,
  "notes": "…" }
```

## 5. App 内「检查更新」（待实现，票 15）

设计要点（避免做成流氓更新）：

- 手动触发为主：设置页「检查更新」；启动时**每天最多静默检查 1 次**，且只提示不打扰
- 流程：`GET latest.json` → 比 `versionCode` → 有新版弹一行动作条「有新版本 m20 · 查看」→
  用户点了才下载 → 下载完提示「安装」
- 下载校验 `sha256`，不匹配就丢弃重下（防劫持/防半截包）
- 安装走 `FileProvider` + `ACTION_VIEW`（`application/vnd.android.package-archive`），
  需要 `REQUEST_INSTALL_PACKAGES` 权限与 `<queries>` 声明
- **不静默安装、不后台自动下大包、不弹全屏广告式弹窗**

## 6. 每次发版的 7 步清单

1. 改 `versionCode` +1，`versionName` 改成 `0.1.0-mNN`
2. `O:\dev\enroute-android\build-test.bat` → 确认 `BUILD SUCCESSFUL` 且单测全绿
3. 真机装一次，跑一遍关键路径（课表 / 空闲教室 / 校园地图 / 登录态）
4. `git add -A && git commit -m "release: mNN …"`
5. `git tag -a v0.1.0-mNN -m "…"` → `git push` + `git push origin --tags`（带代理）
6. 传 APK 与 `latest.json` 到服务器 `/var/www/app/`（路径 B），并生成 GitHub Release 正文：
   - 发版说明用 `tools/release-notes.ps1 -Tag mNN` 生成 —— 自动 `git describe --tags --abbrev=0 mNN^` 取上一 tag，
     拼出「一句话摘要 + `git log 上一 tag..mNN` 的提交标题（去掉 `release:` 那条）+ CHANGELOG 对应小节」，
     落到 `.tmp/release-notes-mNN.md`；
   - Release 正文用 `--notes-file` 引用这个文件，不再把一句话直接塞进 `--notes`：
     `gh release create mNN releases\SYAU-enroute-mNN.apk --title "mNN · <versionName>" --notes-file .tmp/release-notes-mNN.md`
   - **`latest.json` 的 `notes` 仍是一句话**（弹窗里显示空间有限；分条会自动按条渲染，但详细内容归 Release 正文与 `CHANGELOG.md`）
7. 内测群里发一句「已更新到 mNN，更新内容：…」

---

## 7. 回滚

- 服务器**保留上一版 APK**，出问题就改 `latest.json` 指回旧版
- 但 `versionCode` 不能降级 → 回滚要**把旧代码重新打一个新 versionCode 的包**
  （`git checkout <旧tag>` → 改 versionCode 更大 → 重新打包）
- 别删 tag，那是唯一可靠的「回到某个可用状态」的锚点
