## 1. 🔴 Blocker（正确性 / 数据丢失）

### A1 · 刷新覆盖并发状态变更：已读 / 收藏 / 正文标记丢失
**文件**：`data/feed/FeedRepository.kt` L45、L96–108、L122–127；关联 `FeedViewModel.kt` L269（`publish()` 把 `repo.items` 灌回 UI）。

```kotlin
val existing = _items.value.associateBy { it.key }.toMutableMap()   // L45：整轮开始时的快照
for (src in ...) { /* 串行抓取，每源可达数十秒 */ }
...
_items.value = merged          // L126：用旧快照合并结果整体覆盖
store.saveItems(merged)
```

**为什么**：`refresh()` 全程（15 个启用源 × 最多 3 页 + enrich 6 条 × (请求+400ms)，网络差时数分钟）持有 L45 的旧快照。期间用户点开详情（`markRead`）、长按收藏（`toggleStar`）、正文抓取（`ensureBody` 补 `title/summary/deadline/bodyFetched`）都通过 `updateItem` 写进 `_items` 并落盘——刷新结束时 L126 用**不含这些变更**的 `merged` 覆盖内存和 `items.json`。已读红点复活、收藏消失、正文缓存文件还在但 `bodyFetched=false`。
本轮规格 §6.4 明确"刷新中旧数据可滚动可点"、§6.5 新增回前台静默刷新——**并发窗口从"偶发"变成了设计内主路径**。`ensureBody` 的 `updateItem` 与 refresh 尾部同样存在丢更新竞态（读-改-写无互斥，`FeedStore.mutex` 只保护文件写，不保护 `_items` 的合并）。

**修复建议**（二选一，推荐 ①）：
① 把"合并入库"挪到刷新末尾基于**当时最新** `_items.value` 重做：抓取阶段只产出 `List<FeedItem>`（每源解析结果），最后一次性 `existing = _items.value.associateBy{...}` 再走现有 merge 循环；整个"读快照→合并→赋值→写盘"用一把 `Mutex`（或单线程 confinement）包起来，`updateItem/markReadBatch/markUnreadBatch` 共用同一把锁。
② 合并时逐 key 以 `_items.value` 里的当前值为 `old`（而不是 L45 快照），保留 `readAt/starred/bodyFetched/title(补全)` 字段。
验收：刷新进行中点开一条 + 收藏一条，刷新结束后两者状态仍在（可加 repo 层单测模拟交错）。

### A2 · 派生行重算无序竞态 + 陈旧快照：列表可能停留旧结果
**文件**：`ui/feed/FeedViewModel.kt` L161–178（`recompute`）、L262–269（`refresh` 尾部与 `publish` 双写）。

```kotlin
private fun recompute(s: FeedUiState) {
    viewModelScope.launch(Dispatchers.Default) {
        val rows = CATEGORIES.associateWith { ... FeedRows.build(items = s.items, ...) }
        _ui.value = _ui.value.copy(rowsByChannel = rows)   // 无版本校验，后完成者赢
    }
}
```

**为什么**：每次按键（`setQuery`→`recomputeAll`）、每次已读（`publish`→`recompute`）都各自 launch 一个 Default 协程，**完成顺序不保证**。快速输入"竞赛"两个字：若"竞"的计算晚于"竞赛"完成，`rowsByChannel` 最终是"竞"的结果，而 `query` 字段、meta 行"命中 N 条"、chips 都是"竞赛"的——列表与 UI 永久不一致，直到下一次操作。批量已读后同理可能出现"卡片红点已消失但列表还是未读筛选前的行集"。另外 `refresh()` L262 先 copy 一次（items 已新、rows 还旧），`publish()` L269 再 copy 一次并再 launch 一个 recompute——同一帧两次发布 + 两个并发重算，纯浪费且扩大竞态面。

**修复建议**：
- 用单一 `MutableStateFlow<FeedUiState>` + `mapLatest`/`combine` 派生，或最简：`private var recomputeJob: Job? = null`，`recompute` 里 `recomputeJob?.cancel(); recomputeJob = viewModelScope.launch(Default){...}`（cancel-and-replace，天然只留最新输入的产物）；
- 或给状态加单调 `revision`，协程末尾 `if (s.revision == _ui.value.revision) 才写入`；
- `refresh()` 尾部删掉 L262–268 里与 `publish()` 重复的 `items/today` 赋值，只保留 banner/loading/lastSyncAt，然后 `publish()` 一次。

## 2. 🟡 Suggestion（应修：正确性边角 / 数据真实性 / 性能 / 契约）

### B1 · `deadlineFromTitle` 年份启发式会造出"未来截止日"，违背不编造铁律
**文件**：`data/feed/FeedParser.kt` L695–705。
`if (candidate.isBefore(today)) year++`：标题只写"11月13日截止"不带年。12 月抓到的**过期**条目（去年/今年早些的"6月1日截止"）会被推成**明年**，于是"已截止"变"报名中"、倒计时出现一个源里不存在的日期。规格 §8.3/§10.4："只有解析出真实日期才显示……绝不编造日期"。跨年规则对"12 月发 1 月截止"是对的，但对"陈旧条目"是错的，而 jingsai 列表无日期、无法用 publishedAt 判别。
**建议**：加"回溯窗口"约束——候选日在过去 ≤N 天（如 30）内才允许 year++，超过则返回空串（宁可不显示）；或仅当 `today.month==12 && mo==1`（及对称的 1 月→12 月不推）才跨年。把这条边界补进 `NewSourcesParseTest`（现有 4 条断言没覆盖"年中过期标题"）。

### B2 · 标题内嵌年份被忽略
**文件**：`data/feed/FeedParser.kt` L696–704。
`【1月10日截止报名】2027年某大赛`（测试 L171 的原句）在 today=2026-06 时会得出 2026-01-10→推成 2027-01-10，碰巧对；但 `【3月1日截止】2025年回顾展` 在 2026 年会推成 2027-03-01。标题里**写明了年份**时应优先采信。
**建议**：先在标题里找 `(20\d{2})年`，命中且与月日组合合法则直接用；找不到再走启发式（叠加 B1 约束）。

### B3 · `extractDeadline` 会把"比赛/提交截止"当"报名截止"
**文件**：`data/feed/FeedParser.kt` L345–353；`FeedRepository.kt` L211、L221。
规则① `(?:截止|截至)[^。；\n]{0,16}?日期` 不区分语义："作品提交截止：2026-12-01"、"比赛截止 2026-11-30" 都会填进 `deadline`，而 UI 一律渲染成"**报名截止**：…（剩 N 天）"（FeedScreen L1402）并驱动"即将截止"分组与提醒条。对竞赛这是**语义错标**，可能误导报名决策。
**建议**：规则①前加语义锚 `(?:报名|申报|提交材料|报送)` 之一（"报名截止时间"最稳）；抽不到就留空走"时间待定"。至少把"提交/作品"类排除。补正负样本测试。

### B4 · 竞赛平台 `publishedAt = regStart`：时间线语义失真
**文件**：`data/feed/FeedParser.kt` L426；`FeedRepository.kt` L163。
报名开始日当"发布日"：8 月开始报名的赛在"全部"频道永远沉在 8 月桶，11 月才上线的新赛也不进"今天/本周"。注释已声明这是有意取舍，但规格 §3.1"全部保持时间倒序（时间线心智）"被实质改变，且 `firstSeenAt`（真实首见时间）才是无源日期时的诚实排序键。
**建议**：`publishedAt` 留空或保留列表真实发布日（成果公示有 artDate），排序用 `firstSeenAt` 兜底（repo L123 已有 thenByDescending firstSeenAt）；若坚持现方案，至少在详情页把"报名开始"与"发布"两个概念分开展示，避免用户把 08-01 读成通知日期。

### B5 · `parseListCxcy` 对"报名时间"格式漂移零容错，整源静默退化
**文件**：`data/feed/FeedParser.kt` L452–454、L397–399。
`RE_CXCY_REG` 只认 `报名时间：yyyy.mm.dd至yyyy.mm.dd`（含 -/年月日变体）。平台若改成"报名时间：2026-11-06 00:00 至 …"（详情页就是这种带时刻的形态，见 `cxcy_comp_detail.html` L265）或"至"两侧加空格变体，`regStart/deadline` 全空 → 竞赛全部掉进"时间待定"，**列表页仍 200、条数正常、不报错**——最难发现的退化。`RE_CXCY_LINK` 还要求 `title="…"` 非空且 href 在 title 之前，属性顺序一变整行丢弃。
**建议**：① 正则放宽 `\s*至\s*` 两侧空白与可选时刻 `(?:\s+\d{2}:\d{2})?`；② repo 侧加"解析质量哨兵"：cxcy 源 `items.isNotEmpty() && items.all{it.deadline.isBlank()}` 时 `DebugLog.error` 并在 SourceResult 里带 warning（不编数据，只报警）；③ 给 parseListCxcy 补一条"带时刻格式"的 fixture 变体测试。

### B6 · `enrichCxcy` 降级路径的 `contestStart/End` 无条件覆盖 + 限额计数口径
**文件**：`data/feed/FeedRepository.kt` L140–175。
两处：① L166–167 `contestStart = info.contestStart`（非 ifBlank）——对 fresh 条目没问题，但函数签名是通用 List，未来若被复用于老条目会清掉已补窗口；② `n++` 在**请求成功后**才计数（L154），失败请求不占限额：平台大面积 500 时，一轮会对全部 fresh 条目逐条发请求（每条最长 15s 连接超时），"封顶 6 个"的控频承诺失效，且整轮刷新被拖长。
**建议**：`n++` 移到发起请求前（尝试即计数）；`contestStart/End` 改 `ifBlank` 保持与其余字段一致；失败也 `delay(400)` 防紧循环。

### B7 · `refreshIfStale` 的 30 分钟策略在"从未成功"时永不触发
**文件**：`ui/feed/FeedViewModel.kt` L137–148。
`if (last > 0 && now-last > 30min)`：`last==0`（从未成功刷新，但本地有旧缓存 items 非空）时，`refreshIfEmpty` 不抓（items 非空）、`refreshIfStale` 也不抓（last=0）→ 这批缓存**永远不更新**，直到用户手点刷新。规格 §6.5"回到前台 >30 分钟静默刷新"应覆盖此态。
**建议**：`last==0` 视为无穷旧：`if ((last == 0L || now-last > 30min) && !loading) refresh()`。另：跨天重算只发生在 ON_RESUME，前台跨零点不刷新（规格 §8.3 允许"前台期间日期变化检测"，当前未做，见 C 类偏差）。

### B8 · `open()` 缓存命中仍走 ensureBody 的 updateItem + 双 publish
**文件**：`ui/feed/FeedViewModel.kt` L336–350；`FeedRepository.kt` L186–188。
缓存命中路径：`ensureBody` 里 `if (!item.bodyFetched) updateItem(...)` 一次写盘，回来 `if (!cached) publish()` + `markRead` + `publish()`——命中时 `cached=true` 跳过第一个 publish 是对的，但 `markRead` 对**已读条目**也无条件执行（`readAt` 被刷新成最新时间）+ 再 publish 一次。已读重读不应改 `readAt`（规格 §7.2 已读是状态不是时间戳语义），且每次重读都全量写盘 + 全频道重算。
**建议**：`if (item.readAt == null) repo.markRead(item.key)`；publish 合并为一次（markRead 后统一 publish）。

### B9 · `FeedUiState.visible` / `urgentCompetitions` 在组合期做 O(N) 派生，违背派生上移
**文件**：`ui/feed/FeedViewModel.kt` L67–73、L90–94；消费点 `FeedScreen.kt` L170（remember key）、L638（meta 行）、L1016–1017（空态）。
`visible` 每次读取都全量 filter 800 条；`urgentCompetitions` 是 filter+sort 的 getter，`FeedScreen` L170 把它当 `remember` key——**每次重组都重新 filter+sort 一遍**（remember key 按结构相等比较，内容不变时缓存值会保留，但"算 key"本身的 O(N) 开销每次重组都付）。`deadlineBarVisible()` 里的 SharedPreferences 读取在内容变化时随之执行。规格 §11.1"pager 页组合体内禁止裸 filter"的精神被这两个 getter 绕过了。
**建议**：`urgentCompetitions` 与 `visible.size`（meta 行只要计数）在 `recompute` 里一并算好存进 `FeedUiState`（如 `urgentKeys: List<String>`、`filteredCountByChannel: Map<String,Int>`）；`deadlineBarVisible` 改为纯状态字段（dismiss 时更新），不在组合期读 Prefs。

### B10 · 每卡重复读 CompositionLocal + 每卡 remember 开销
**文件**：`ui/feed/FeedScreen.kt` L790、L901、L967（`InkTokens.current` 在 StandardCard/CompactCard/StarMark 内）；L793–795、L904–906（每卡 `remember(deadline,category,today)`）。
规格 §11.11 明确"InkTokens 在列表容器层读一次下传，禁止每卡重复查询"。当前每张卡 1–3 次 local 查询；`deadlineLabel` 是纯查表级计算（一次 LocalDate.parse），按审计规则"trivial 计算不值得 remember 的 slot 开销"，30+ 卡 × 3 key 的槽位与比较成本反而更高。
**建议**：`FeedPage` 读一次 `t` 下传（或经 `CompositionLocalProvider` 已有的上层直接传参）；`dl` 改普通 `val`（`FeedRows.deadlineLabel` 内部可把 parse 结果缓存到 item 派生阶段，见 A2 修复时顺带）。

### B11 · 浮层滑入动画在 Composition 读动画值
**文件**：`ui/feed/FeedScreen.kt` L1112–1135（SheetScaffold）；同型 `CourseQuick.kt` L81–109、`CourseDetail.kt` L90–117、`EnRouteRoot.kt` L90–100（tab 指示条）。

### B12 · `loadMore` 的 total 用未过滤计数，筛选态下窗口虚增
**文件**：`ui/feed/FeedViewModel.kt` L212–219。
`val total = s.totalOf(category)` 是**未过滤**总数；筛选后命中 5 条、频道总 300 条时，`cur(30) < 300` 恒成立，每次触发都 +30 直到 300（有界，但远超实际需要的 5）。叠加 B13 的到底误触发，筛选态下窗口会被推到频道总量级（内存/重算浪费，且"窗口重置 30"语义被破坏）。
**建议**：total 用该频道**过滤后**条数（`rowsByChannel[cat]` 的 Footer.total，或 B9 的 filteredCount）；`cur >= filteredTotal` 即 return。

### B13 · 分页触发信号把"页脚可见"当成"需要加载"，边沿触发在特定视口下停摆
**文件**：`ui/feed/FeedScreen.kt` L689–697；`ui/feed/FeedRows.kt` L177（Footer 恒存在）。

```kotlin
val shouldLoadMore by remember(rows.size) {
    derivedStateOf {
        val last = listState.layoutInfo.visibleItemsInfo.lastOrNull()?.index ?: 0
        last >= rows.size - 5
    }
}
LaunchedEffect(shouldLoadMore) { if (shouldLoadMore) onLoadMore() }
```

**为什么**：`FeedRows.build` 无论是否还有剩余都追加 Footer，所以**只要页脚可见（或进入预取区），`last ≥ rows.size−5` 就恒真**——信号退化成"页脚是否可见"，不携带"是否还有更多"。三个后果：

1. **到底后持续空调**：已到底时页脚常驻可见，条件恒真；每次 `rows.size` 变化（折叠/展开、刷新、已读）重建 derivedState 并重跑 effect → 空调 `loadMore`，全靠 B12 那个不总有效的下游 guard 兜底。
2. **边沿触发 + 恒真 = 潜在停摆**：`LaunchedEffect(shouldLoadMore)` 只在布尔**翻转**时跑。长列表正常路径（首帧 layoutInfo 空→false，滚近尾部→true）能工作；但**短列表/大视口**（内容总高 < 视口，全部行可见）布局完成后条件直接恒真且永不翻转——若 effect 首次执行恰在 layoutInfo 填充前（`last=0`，33 行时 0≥28 为假），之后无翻转就**不再触发**，列表停在第一窗、页脚写"上滑加载"却无东西可滑。是否踩中取决于 effect 与首帧布局的先后，平板/横屏/紧凑卡频道风险最高。
3. 规格 §6.1 语义是"最后可见索引 ≥ 已渲染数−5 **且还有更多**"，现实现把"还有更多"完全外包给下游。

**修复建议**：把"是否还有更多"纳入信号，并对**索引值**而非布尔做响应（每次滚动都重评估，短列表首帧布局后即触发；到底后 `hasMore=false` 不再空调）：
```kotlin
val footer = rows.lastOrNull() as? FeedRow.Footer
val hasMore = footer != null && footer.shown < footer.total
val lastVisible by remember { derivedStateOf { listState.layoutInfo.visibleItemsInfo.lastOrNull()?.index ?: -1 } }
LaunchedEffect(lastVisible, rows.size, hasMore) {
    if (hasMore && lastVisible >= rows.size - 5) onLoadMore()
}
```
建议把判定抽成纯函数 `shouldLoadMore(lastVisible, rowCount, shown, total)` 放进 FeedRows，补"窗口=30、总 45、全部可见"与"已到底"两条断言。

### B14 · 长按菜单/页头菜单读的是打开瞬间的 item 快照，状态不随刷新更新
**文件**：`ui/feed/FeedScreen.kt` L143（`quickItem`）、L261–268、L1186–1248（FeedQuickActions）。
`quickItem` 存的是长按那一刻的 `FeedItem` 值。菜单打开期间若刷新完成（A1 修复后仍会有 items 更新）或另一处改了已读/收藏，菜单头部"未读/已读"、row01/row02 文案、复制内容都用旧快照；点 row01 时 `onSetRead(unread)` 的 `unread` 也是旧值，可能把刚被别处标已读的条目又标一次（幂等，无害）或把刚标未读的又标回已读（有害）。
**建议**：菜单内按 `quickItem.key` 从 `ui.items` 取最新条目渲染（`val item = ui.items.firstOrNull{it.key==quickItem?.key} ?: quickItem`），动作回调也用最新状态。低概率但属状态一致性。
