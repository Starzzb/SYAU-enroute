## 1. D1 耗时字段

### 输出格式（真实代码产物，非手写示例）

```
11:20:01.200  [URP] ← 200 12.3KB 820ms GET jwc.syau.edu.cn/index/jwtz.htm
11:20:01.100  [URP] ← 302 0B 640ms GET 10.2.0.47/login?ticket=***
```

- 格式：`← <状态码> <字节> <耗时ms> <方法> <短URL>`
- `elapsedMs < 0`（未计时）时**不输出**耗时段 —— 老调用点不受影响。
- 计时器用 `System.nanoTime()`（不受系统时间被调整影响）：
  - URP：`UrpClient.request()`（所有教务请求的唯一咽喉）
  - 抓取：`FeedHttp.get()`（自计时并回填 `Resp.elapsedMs`）
- 每源日志：`教务通知：820ms · 1 页 · 15 条`
- 整次刷新：`刷新总计 8123ms · 14 源（成功 11 / 失败 3）· 新增 26 条，本地共 380 条`
- `SyncReport.elapsedMs` 已加（UI 想显示「本次刷新用时」直接用）。

**真机实测（2026-11-14 17:54，15 源刷新，lead 实机采集）**：

```
← 200 92.1KB  988ms  GET www.cahe.edu.cn/site/term/373.html
高教学会：1017ms · 1 页 · 5 条
我爱竞赛网：760ms · 1 页 · 4 条
刷新总计 13775ms · 15 源（成功 15 / 失败 0）· 新增 0 条，本地共 316 条
```

**结论**：一屏就能看出哪个源慢 —— 13775ms 里高教学会（1017ms）与竞赛网（760ms）占大头，
这正是「抓取并行与条件请求」需要的基线。

## 2. D2 落盘

### 位置与命名

```
<filesDir>/debug/2026-11-14.log     ← 按天一个文件，只追加不重写
```

- 行格式与 `dump()` **共用** `DebugLog.formatLine()`：`HH:mm:ss.SSS  [TAG] 消息`，UTF-8。
- flush 策略：**每 20 行或每 500ms**（不指望 `onTerminate`，Android 常不调用）——
  崩溃前最后几行尽量落盘。
- 上限：`MAX_DAYS = 7`、`MAX_BYTES = 2MB`，启动时 `rotate()` 一次，超了从最旧的删。
- 开关：`Prefs.debugLogToFile`（**默认开**，release 同样生效，没用 `BuildConfig.DEBUG` 写死）。
  关掉后 `attachFile(null)`，**连文件都不再创建**。

**JVM 已验证**（`DebugLogFileTest`）：轮转只留 7 天且删最旧、3MB → 裁剪到 ≤2MB、
清空历史、行格式一致性。

**真机实测（2026-11-14，lead 采集）**：

- 调试页标题行从空白修好后显示 **`19 条 · 落盘 25KB`**，并随日志增长 **16KB → 23KB → 25KB**（数值真的在动）
- 导出文件名从 `在途日志_2026-11-14_2026-11-14.txt` 修成 **`在途日志_2026-11-14.txt`**（单日不再重复）
- 「导出全部」全流程通：SAF 弹窗 → 保存成功 → 屏幕提示「已导出全部历史日志」
- **不是缺陷的观察**：曾出现一次「内存 0 条 · 落盘 23KB」，复测为**冷启动后探针尚未跑完**的时机问题，
  内存缓冲本来就从 0 开始涨 —— 不记为 bug。

## 3. 脱敏（红线）

### 命令级证据

生成器：`DebugLogEvidenceTest` 把 6 行真实形态的敏感日志写进
`app/build/debuglog-evidence/2026-11-14.log`（343B，不自动删除）。

脱敏后的**实际文件内容**（原样粘贴）：

```
11:20:01.100  [URP] ← 302 0B 640ms GET 10.2.0.47/login?ticket=***
11:20:01.200  [URP] ← 200 12.3KB 820ms GET jwc.syau.edu.cn/index/jwtz.htm
11:20:01.300  [SESSION] Set-Cookie: ***
11:20:01.400  [SESSION] Set-Cookie: ***
11:20:01.500  [CRED] POST body password=***&execution=***
11:20:01.600  [API] GET api/score?token=***&access_token=***
```

校验命令与结果：

```powershell
Select-String -Path app\build\debuglog-evidence\*.log `
  -Pattern 'JSESSIONID=[^*.\s]|CASTGC=[^*.\s]|ticket=[^*.\s]|token=[^*.\s]|password=[^*.\s]'
# → NO PLAINTEXT CREDENTIALS FOUND (0 matches)
```

### 覆盖的模式

| 类别 | 例子 | 结果 |
|---|---|---|
| Cookie / Session | `JSESSIONID=…`、`CASTGC=…`、`student.urpSoft.cn=…`、`PHPSESSID=…` | `***` |
| CAS 票据 | `lt=…`、`ticket=…`、`execution=…`、`service_id=…` | `***` |
| 密码字段 | `password=`、`pwd=`、`passwd=`、`pl=` | `***` |
| 通用 token | `token=`、`access_token=`、`refresh_token=`、`secret=`、`api_key=` | `***` |
| 头部形态 | `Authorization: …`、`Cookie: …`（含 `Set-Cookie:`） | 值整体 `***` |

> 头部形态（`Set-Cookie:` / `Cookie:`）会**整段值**替换成 `***`（连 cookie 名一起），
> 这是有意的：cookie 名是数据库里可能新增的，白名单挡不住未知名字，只有整体抹掉才安全。
> 代价是「知道有个 cookie」这条信息丢了 —— 可接受，安全优先。

`DebugLogFileTest` 另覆盖：脱敏保留键名、普通文本不误杀、落盘文件搜不到三个真值。

> **验收口径（别写成"真机已验证通过"）**：截至本文档更新，
> 脱敏已通过的是**代码层实现 + 合成证据 0 命中**（本机 JVM、四条下游路径的产物）；
> **真机那三个串（`ST-…` / `studentId"` / `Ob67Fhu5HY`）的复验要等下一版包**。

## 4. D3 分级与错误保底

- `Level = DEBUG / INFO / WARN / ERROR`
- 映射：`log()→INFO`、`step()→DEBUG`、`error()→ERROR`、`http()` 按状态码
  （2xx→INFO、4xx/5xx→WARN、-1/异常→ERROR）。
- **ERROR 保底**：主缓冲 400 条之外，另存最近 **50 条 ERROR**（独立 `StateFlow`）。
- 过滤只在**读取侧**（调试页 chips：全部 / 警告+ / 仅错误），写入侧不丢数据。

**JVM 已验证**：灌 3 条 ERROR + 500 条 DEBUG 后，主缓冲里那 3 条已被冲掉，
但「仅错误」仍能拿到 3 条；灌 60 条只留最近 50 条且顺序正确（e10…e59）。

**真机实测（2026-11-14，同一会话）**：全部 **91 条** / 仅错误 **8 条**；
点「仅错误」列表确实只剩 8 条，FEED 的批量 HTTP 噪音被正确滤掉 ——
「过滤只在读取侧」的设计在真机上生效。

## 7. 真机复测后的修正（2026-11-14 晚）

真机抓到 **CAS 票据 `ST-277817-…` 明文显示在调试页上** —— 说明「只在落盘那层脱敏」不够。

| 出口 | 走的路径 | 旧行为 | 现在 |
|---|---|---|---|
| ① 屏幕 | `DebugLog.entries` → 调试页 | ❌ 明文 | ✅ 已脱敏 |

### 新增的三组规则（`DebugLogFile.redact`）

1. **敏感 JSON 键**（抹值留键）：`studentId / student_id / studentNo / xh / sid / userName / realName / idCard / sfzh`
   → `"studentId":"***"`
2. **学号形态兜底**：`(?<!\d)20\d{8}(?!\d)` —— 10 位、20 开头。
   特意卡长度边界：`courseNumber`（9 位）、`20250101`（8 位日期）**不误伤**。
3. **路径段随机 token**（先点名后通用）：
   - `NAMED_RANDOM_SEGMENT`：`/(scoreQuery|courseQuery|examQuery|gradeQuery|calendarQuery)/<任意>/` → `/scoreQuery/***/`
   - `MIXED_ALNUM_SEGMENT`：6–24 位、**同时含字母和数字**的路径段 → `/***/`
     （要求「混合」所以 `allPassingScores`、`callback`（纯字母）、`901040351`（纯数字）都不动）

### 关于「兜底 + 白名单」的建议 —— 采纳一半，理由如下

- **采纳**：敏感键名逐键抹（第 1 条），这是「以后换接口也不会漏键名」的部分。
- **不加**「响应体只保留 180 字符」之外的更激进截断：预览已经是 `take(180)` 且压成一行的，
  真正的兜底是**键名表 + 形态规则**；把预览截到 60 字符会让「接口改版」这类问题反而看不出线索。
- **不做**全量白名单化（只留白名单字段）：教务字段名没有稳定契约，白名单会直接把有用信息全砍掉，
  与「日志要能诊断」冲突。现在的组合是：具体模式（票据/Cookie/密码/token）+ 键名表 + 学号形态 + 路径段形态，
  四层叠加后再靠 180 字符预览收敛暴露面。

**单测**：`DebugLogFileTest` 15 条（新增 `学号与路径段随机token也要抹掉`，含不误伤断言）+
`DebugLogEvidenceTest` 1 条。**当前 455 条 / 36 类 / 0 失败**。
