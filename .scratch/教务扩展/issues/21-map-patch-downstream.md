# 21: 地图补丁**下行**同步（把别人的补丁实时拉给客户端）

**What to build:** 客户端定期 `GET` 远端补丁并合并显示，这样别人补的属性不必等发版就能看到。

**Blocked by:** 无（但**不建议现在做**，见下）

**Status:** wontfix（设计决定，不是"暂时缺接口"）

---

## 为什么标记 wontfix

### 1. 服务端没有这个接口，而且不是"加个路由"就完
`tools/map/server.js` 目前只有 `POST /map/api/patches`、`GET /map/api/health`、
`GET /map/api/snapshot`（需 `X-Admin-Key`）。要做下行至少要补：
- `GET /map/api/patches?mv=&since=` 的游标与分页
- `reviewed` 过滤（只发人工审核过的）
- 快照/增量的一致性（客户端断点续拉）

### 2. **未经审核的众包数据不能直接展示给其他用户**（红线）
众包的**价值在覆盖，风险在质量**。别人随手填的「层数=99」或错位的「所属单位」，
如果实时下行，会让一批用户的地图上出现**错误信息**，而且错误会带着"官方"的权威感传播。
唯一可靠的门是**人**：内测期每条数据都应该过一眼。

### 3. 现有链路已经能跑，且每一步都有人参与
```
客户端（默认关，手动上报）→ POST /map/api/patches → /var/lib/campusmap/patches.jsonl
   → tools/map/merge_edits.py（幂等 + 不动点有单测）→ conflicts.txt 人工过一眼
   → tools/map/pack.py --from-geojson → assets/map/campus.geojson + manifest.customFields
   → 随版本发布 → 用户更新 App → 官方基线以只读层出现（标「官方」，不计入「已标注 N」）
```
延迟是「一次发版」，换来的是一次人的判断。内测期这个交换是划算的。

## 什么情况下应该重开这张票

同时满足才值得做：
- [ ] 补丁量级上来了（比如每周几十条），人工合并变成瓶颈
- [ ] 有了审核流程/后台（`rev` 能可靠置 1，最好有第二人复核）
- [ ] 服务端补上增量接口与 `reviewed` 过滤，并有「客户端如何回滚一条脏数据」的方案

## 现在的替代做法

- 用户想立刻看到别人补的内容 → 发一次版（合并链路已在票 13 落地）
- 运营侧视图：`GET /map/api/snapshot`（admin）随时能拉全量审核结果
