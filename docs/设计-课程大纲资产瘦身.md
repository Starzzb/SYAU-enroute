# 课程大纲资产瘦身方案（实测数据 2026-11-17）

> 起因：App 里已有土环 167 门大纲；14 个学院 2066 门全部收完之后，「资产占用」会变成 APK 的主要重量。
> 本文所有数字都是在 `在途/curriculum/` 的真实产物上跑出来的，复现脚本在 `在途/curriculum/_work/`。

## 0. 结论先放

1. **内容压不动**。2066 门、35.02 MB 是真实正文；gzip 后 7.46 MB（20.3%），空白规范化只再省 1.6%，跨课程重复段落只值 1.4%，按课程代码去重只值 1.0%。**不要再在「压缩/去重」上花力气。**
2. **能减的只有三处**：合包（省 32%）、投递方式（索引常驻 + 正文按需）、仓库里的生成物（27.9 MB 松散对象）。
3. **推荐 C**：全量索引（35 KB）打进 APK，正文按学院分包、首次用时下载并缓存。**APK 常驻增量从「+7.5 MB 到 +11.0 MB」变成「+0.04 MB」**，现有土环那 2.88 MB 也能一并挪出去。
4. **培养方案走另一条路**：它必须离线，但课程行跨专业重复达 62%（17232 行只有 5574 个不同文本），抽共享池后 1.16 → **0.57 MB**，继续内嵌（详见 §6）。两条线一起做，**APK 5.16 → ≈3.6 MB**。

## 2. 四种「以为能省」的路，全测过

| 想法 | 实测收益 | 判定 |
|---|---|---|
| 逐文件 gzip / 再压一层 | 0（AAPT 已做） | 无用 |
| 空白规范化（多空格合并、CJK 间空格删除） | 35.02 → 34.45 MB，**1.6%** | 不划算，正文已干净 |
| 完全相同段落抽共享池 | 828 个文本 / 1729 处重复 → **0.39 MB（1.4%）** | 不划算 |
| 按课程代码跨学院去重 | 2033 个代码里重复 19 个 → **0.36 MB（1.0%）** | 不划算 |

> 重复的大头只有两类：公共课体育课的**解析缺陷**（代码字段里塞了 `902031101、902031102、\n902031103、902031104` 四个码粘连，需在 `syllabus.py` 里规范化，属于 bug 不是资产问题），以及跨学院同开课（风力发电、微生物学Ⅰ等）。

## 4. 四个交付方案

| 方案 | assets 常驻 | APK 增量 | 离线能看的 | 端上改造 | 判断 |
|---|---|---|---|---|---|
| **A** 全量、每门一文件（延续现状做法） | 35.3 MB | **+11.0 MB** | 全部 | 无（加文件即可） | 直接否决：APK 5.16 → ~16 MB |
| **B** 全量、14 个学院包 + 全量索引 | 35.4 MB | **+7.5 MB** | 全部 | 中：读法改成「解包扫行」 | 只在「必须全离线」时选 |
| **C** 索引 + 土环包进 APK，其余 13 个学院按需下载 | 3.2 MB | **+0.7 MB**（比现在还少 1.5 MB） | 索引全部课程名/学分/学时 + 土环正文 | 中：加一个下载缓存层 | **推荐** |
| **D** 内容裁节（丢 一、三 节与学时一览表） | 30.5 MB | +6.5 MB | 全部 | 小 | 省 13% 但丢信息，且 D 可以叠加在 B/C 上 |

> 若连土环也外包（方案 C 的满血版）：assets 常驻只剩索引+META ≈ 0.1 MB，**APK 5.16 → ~3.2 MB**，比现在少 2 MB。

## 5. 推荐落地：两阶段，都能单独上线

### 第 1 阶段（不改变离线能力，纯打包改造）

1. `在途/curriculum/_work/pack.py` 已产出：全量索引 `json/pack/syllabus_index_all.json`（2066 条，0.38 MB 紧凑 / 35 KB gz）+ 14 个学院包。
2. 把 `assets/curriculum/syllabus_*.json`（167 个文件）换成 `assets/curriculum/packs/土地与环境学院.jsonl.gz` + 新索引，**APK 立刻省 0.25 MB 左右，且序列少了 166 个文件**（构建期 asset 合并也更快）。
3. 读法：`CurriculumAssets.syllabus(id)` 改为「按索引找到所在包 → 解 gz 流式扫到第 N 行 → 解析」。索引里增加三个字段：`college`、`pack`、`line`。

索引条目（已生成，向后兼容，只是多了字段）：

```json
{"id":"901041603","code":"901041603","name":"GIS空间数据…","type":"实验课",
 "credit":"1","hours":["20",""],"college":"土地与环境学院",
 "pack":"土地与环境学院.jsonl.gz","line":0}
```

### 第 2 阶段（其余 13 个学院改为按需下载）

1. 13 个包（合计 ~6.8 MB）与索引一起挂到现有更新通道同一仓库：`Starzzb/SYAU-enroute`，路径 `releases/packs/<学院>.jsonl.gz`；沿用 `UpdateCenter.kt` 已有的候选地址链（`gh-proxy.com` → `raw.githubusercontent.com` → `raw.githack.com`），不新造一套下载器。
2. App 侧新增 `SyllabusStore`：`filesDir/curriculum/packs/` 下缓存解压后的 jsonl；LRU 上限 2 个学院（最大 3.76 MB 紧凑文本），超限淘汰最久未用。
3. UI 语义（守数据诚实）：
   - 索引命中但学院包未下载 → 「**正文需下载**（约 0.8 MB）」而不是「无大纲」；
   - 下载失败 → 「推送失败」+ 手动重试，绝不显示空白正文冒充；
   - 索引进 APK 保证 `hasSyllabus()` / `matchSyllabus()` 的**判断全部离线可用**，只有正文会缺。
4. 下载只在用户点开某门课时触发，不做后台预取（省流量，也别在别人网里偷偷跑）。

## 6. 培养方案那 7.33 MB 怎么办（另一条线，收益比大纲大）

培养方案（`assets/curriculum/plan_*.json`，168 份 + 索引）和课程大纲的**访问形态不同**：它是「选年份 → 选专业 → 看整份方案」的**核心浏览数据**，必须离线；而大纲是「课表里某门课顺手查」，稀疏访问。所以两者该用不同策略。

### 6.1 现状与字段构成

| 年份 | 份数 | 原始 | 均份 |
|---|---|---|---|
| 2023 | 55 | 2.31 MB | 43.1 KB |
| 2024 | 67 | 2.77 MB | 42.4 KB |
| 2025 | 46 | 2.23 MB | 49.7 KB |
| 合计 | 168 | **7.32 MB 紧凑** | 逐份 gz 合计 **1.16 MB** |

字段占比（全部 168 份）：

| 字段 | 体积 | 占比 |
|---|---|---|
| **课程设置与教学进程** | 4.77 MB | **62.0%** |
| 毕业要求列表 | 1.00 MB | 13.0% |
| 毕业要求 | 0.86 MB | 11.2% |
| 培养目标 | 0.28 MB | 3.6% |
| 课程替代情况说明 | 0.18 MB | 2.3% |
| 学分结构表 | 0.17 MB | 2.2% |
| 其余 14 个字段合计 | 0.44 MB | 5.7% |

### 6.2 关键发现：课程行在跨专业/跨年重复得很厉害

`课程设置与教学进程` 共 **17232 行，只有 5574 个不同文本** —— 公共课、学科基础课在几十个专业的方案里一字不差地重复。抽成共享池（行 → 池下标）：

| 形态 | 体积 |
|---|---|
| 现状：168 份各自 gz | **1.16 MB** |
| 每份保留原文件、课程行换成池下标 + 共享池单独一个 asset | 0.80 + 0.12 = **0.92 MB**（省 21%） |
| 共享池 + 3 个年包（一行一份方案） | 2023 0.14 + 2024 0.14 + 2025 0.17 + 池 0.12 = **0.57 MB（省 51%）** |
| 共享池 + 全部塞进一个 blob | 0.57 MB（与上者同体积，但失去了按年懒加载） |

**推荐第三行**：`assets/curriculum/plans/pool.json`（1.48 MB 紧凑 / 0.12 MB apk）+ `2023|2024|2025.jsonl`（各 0.93–1.10 MB 紧凑）。进「培养方案」页时只解当年那一个包（最大 1.10 MB），池按 `List<String>` 常驻（约 3 MB 堆），取某份方案时只展开它用到的那 ~100 行。

### 6.3 试过但不划算的

| 想法 | 实测 | 判定 |
|---|---|---|
| 只留最新学年（2025） | 省 0.31 MB（27% 的份数） | 砍数据，2023/2024 的转专业与对比要用，不干 |
| 新版相对旧版做差分（43 个专业两版相似度 0.83–0.90） | 抽完池后剩余多为各专业独有的目标/要求文本 | 收益 < 0.1 MB，复杂度不值 |
| 由 `毕业要求列表` 重建 `毕业要求` 整段文本 | **168 份全部不可精确重建**（编号与换行不一致） | 不做 —— 数据诚实优先 |
| 由 `培养目标列表` 重建 `培养目标` | 168 份全部不可精确重建 | 同上 |

### 6.4 结论

培养方案**继续内嵌、但换打包形式**：1.16 MB → **0.57 MB**，文件数 168 → 4。它不参与「按需下载」，因为它是离线浏览主路径；把下载留给大纲正文。

叠加之后的总账：

| 项 | 现在 | 改造后 |
|---|---|---|
| 培养方案 | 1.16 MB | **0.57 MB** |
| 大纲（土环 167 门） | 0.89 MB | 0（正文走下载），索引 0.035 MB |
| META / 索引 | 0.01 MB | 0.05 MB |
| **assets 在 APK 内合计** | **2.17 MB** | **≈0.65 MB** |
| **APK** | **5.16 MB** | **≈3.6 MB**（还能覆盖 2066 门大纲的索引） |

## 7. 仓库侧：这 27.9 MB 也不该背着

`git count-objects -vH` → `size: 27.92 MiB`，`packs: 0`（从未 repack）。已跟踪的大头全是**生成物**：

| 文件 | 体积 |
|---|---|
| `在途/curriculum/json/课程行_全部.jsonl` | 6.80 MB |
| `在途/curriculum/json/培养方案_2024.json` | 4.56 MB |
| `在途/curriculum/json/培养方案_2023.json` | 4.50 MB |
| `在途/curriculum/json/培养方案_2025.json` | 4.03 MB |
| `在途/curriculum/json/课程总索引.json` | 3.85 MB |
| `在途/curriculum/json/课程大纲_2021_土地与环境学院.json` | 3.02 MB |

建议：`在途/curriculum/json/` 里的**解析产物**（不是抓取脚本）按生成物处理 —— `.gitignore` 掉 `课程大纲_2021_*.json`、`课程行_*.jsonl`、`pack/`；保留 `_work/*.py`、`_collect/*.py`、`pack_report.txt` 这类「怎么生成」的东西。培养方案 JSON 若已被 App 构建脚本依赖，则改为构建期从源生成，不入库。

## 8. 验收标准

- `:app:compileDebugKotlin` 过；新增 JVM 单测锁住：索引能解析 2066 条、按 `pack+line` 取回的课程与源 JSON 逐字段相等、包缺失时 `syllabus()` 返回 null 而不是空对象；培养方案池展开后与原 `plan_*.json` 逐字段相等（168 份全量比一遍）。
- `build-release.bat` 出的 APK 体积对比记录在本文件（当前基线 5.16 MB；培养方案改造后预期 ≤4.6 MB）。
- 真机：任意一门非土环课程，首次点开触发下载 → 显示正文；断网点开 → 「正文需下载」而不是空白。
