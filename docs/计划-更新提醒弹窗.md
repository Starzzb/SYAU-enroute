# 计划：更新提醒弹窗

> 交给主代理执行。目标：静默检查发现新版本后，**在启动完全加载之后**弹窗提醒，
> 说清楚更新了什么，给三个出口：`立即更新` / `我知道了` / `不再提醒本次更新`。
>
> 主人原话（2026-11-16）：
> 「在启动完全加载之后弹，频率只要不更新就弹，但要给个不再提醒本次更新的可选，
> 另一个是我知道了和立即更新。要说明更新内容。」
>
> **设计方向已定稿（2026-11-16）**：采用 **方案 B「里程表」**——
> 版本号做成机械翻页（`m19 → m20` 逐位滚上去），标题「该翻表了」，
> 更新内容为带 `·` 前缀的列表，`立即更新` 独占一行，
> 「我知道了 / 不再提醒」两个次要按钮同行。
>
> 四个候选方案的并列对比见 `docs/更新弹窗-对比.html`；
> 方案 B 的独立精修预览见 `docs/更新弹窗-B.html`。

## 1. 行为规格（这是本轮的核心，先定死再写代码）

### 1.1 触发时机

**必须在"启动完全加载之后"**，不是 `onCreate` 立刻。

判定条件（三者同时满足才弹）：

1. 主界面已完成首帧 —— 用 `withFrameNanos {}` 或 `LaunchedEffect` + 一次 `delay`，
   与 `MainActivity.kt:101` 既有的"首帧之后才做事"纪律一致。
2. **不在启动动画/骨架屏期间** —— 资讯页首抓、课表读取都应在弹窗前落定。
   建议：首帧后再等 `500ms`，或者等 `ui.loading == false`。
3. 没有其它弹层正在显示 —— 避免和 `CourseDetailOverlay`、`SheetScaffold`、
   `AlertDialog`（地图/资讯页已有多个）叠在一起。需要先确认当前无活动弹层。

> ⚠️ **不要在 `Application` 里弹**：没有 Activity 上下文。检查在 Application，
> 展示在 UI 层，两者通过状态流连接。

### 1.2 弹窗频率（主人指定）

> **只要不更新就弹。**

即：**每个新版本弹一次，用户没更新就下次启动继续弹**。

| 场景 | 是否弹 |
|---|---|
| 有新版本，用户点了「我知道了」 | ✅ **下次启动继续弹** |
| 有新版本，用户点了「不再提醒本次更新」 | ❌ 该 `versionCode` 永久不再弹 |
| 有新版本，用户点了「立即更新」但下载失败/取消 | ✅ 下次启动继续弹 |
| 有新版本，用户更新成功 | ❌ 版本已追平，无新版可弹 |
| 服务器又发了更高版本 | ✅ 弹（因为 `versionCode` 变了） |
| 用户直连下过新版但没装 | ✅ 仍弹（本机 `VERSION_CODE` 未变） |

**实现要点**：只记录"不再提醒"的 `versionCode`（单个 Long 即可，不用集合）。
判断逻辑：`available.versionCode == dismissedCode` → 不弹；否则弹。

> 「不再提醒本次更新」的语义边界要说清：它只压制**这一个版本号**，
> 不是"永久关闭更新提醒"。服务器发下一版照样弹。这是主人要的语义，别做成全局开关。

### 1.3 强制更新（`isMandatory`）

`UpdateVersions.isMandatory()` 为 true 时（本机 `versionCode < minSupported`）：

- **仍然弹**，且文案更明确（"这个版本太旧，部分功能可能已经不可用"）
- **「不再提醒本次更新」不可用**（隐藏或禁用）—— 强制更新不该被静默
- **「我知道了」保留**，因为票 15 红线是"**绝不阻断使用**"（`UpdateManifest.kt:188` 注释明确）。
  即：可以催，不能锁死。

### 1.4 三个按钮

| 按钮 | 行为 |
|---|---|
| **立即更新** | 跳到设置页 `UpdateSection` 并**自动开始下载**（不是只跳页面让用户再点一次） |
| **我知道了** | 关闭弹窗；下次启动继续弹 |
| **不再提醒本次更新** | 关闭弹窗 + 记下该 `versionCode`；后续不再为这个版本弹 |

### 1.5 按钮布局（**已定稿：方案 B「里程表」，2026-11-16 主人选定**）

```
┌─────────────────────────────────────────┐
│         [    立即更新    ]               │   ← 独占一行，主色实心
├──────────────────────┬──────────────────┤
│        我知道了       │     不再提醒      │   ← 同行，同等次要
└──────────────────────┴──────────────────┘
```

**为什么这么排**：

| 按钮 | 语义重量 | 视觉权重 | 理由 |
|---|---|---|---|
| 立即更新 | 中 | **最强**（主色实心，独占一行） | 唯一推进动作 |
| 我知道了 | 轻 | 中（描边，等分） | 常规延后，不推进也不拒绝 |
| 不再提醒本次更新 | **重** | 中（描边，等分） | 与「我知道了」同级并列 —— 见下方说明 |

> **与方案 D 的关键差异**：D 把「不再提醒」压成纯文字、视觉最弱；
> B 让它与「我知道了」**同级并列**。
> 取舍：B 更清晰（两个"暂不更新"的选择一眼可比），代价是「不再提醒」的误触风险略高。
> **主人选定 B，以本文为准。**
> 若要降低误触，可把该按钮文案写全为「不再提醒**本次**更新」并保持等宽——
> 让用户读完整句再点。**不要**用"变灰"来表达弱化。

**强制更新时的差异**（见 1.3）：`isMandatory == true` 时**整块移除**「不再提醒本次更新」，
底部只剩「立即更新」+「我知道了」。此时「我知道了」仍在——票 15 红线是绝不阻断使用。

**触区**：三个按钮各 ≥48dp 高。

> **关于「立即更新」落到哪里**：两个选择——
> (a) 跳设置页，由用户点「下载」；
> (b) 跳设置页并自动触发下载。
> 建议 **(b)**，因为用户已经表达"立即更新"的意图，再让他点一次是多余的一步。
> 实现上给 `UpdateSection` 加一个 `autoStart: Boolean` 入参。
> 注意已有交互契约：**未确认前不下载**（`UpdateSection.kt:55`）——这里"点立即更新"就是确认。

## 2. 弹窗内容规格

### 2.1 必须显示的信息

| 字段 | 来源 | 说明 |
|---|---|---|
| 标题 | 固定文案 | 例：`发现新版本 0.2.0+m20` |
| 当前版本 → 新版本 | `BuildConfig.VERSION_NAME` / `UpdateInfo.versionName` | 让用户知道从哪到哪 |
| **更新内容** | `UpdateInfo.notes` | **主人明确要求"要说明更新内容"** |
| 包大小 | `UpdateInfo.sizeText`（`UpdateManifest.kt:32`） | 附带信息，让用户判断流量 |
| 强制提示 | `isMandatory` | 见 1.3 |

### 2.2 `notes` 的呈现（关键细节）

`latest.json` 当前的真实内容：

```
"notes": "地图属性共建、自定义课程、2023 级培养方案、账页主题、调试日志；
          修复教师搜索崩溃、空闲教室查不出结果、登录态反复失效、地图拖动回弹"
```

特点：**用 `；` 分隔的短句串，长度约 60–120 字**。呈现规则：

1. **按 `；` / `\n` 切分成条目**，顺序编号 `01 / 02 / …`（方案 D 的编号即来自这里）
2. **`、` 不再切分**——一个分句内用顿号并列的，属于同一条（如「账页主题、调试日志」是一条）
3. **最多显示 8 条**，超出显示「等 N 项」并可展开；不多于 8 条时不显示任何计数
4. `notes` 为空时**整块不显示**（连分隔线一起隐藏），不要写"暂无更新说明"（不编数据）
5. **主体可滚动**，页脚固定（见 2.3）
6. ⚠️ **不要臆测「哪条是新增、哪条是修复」**：`notes` 是自由文本，没有结构标记。
   当前只有 `notes` 字符串的情况下，统排为一列（无分区标题），不猜测语义。

### 2.3 版式（**已定稿：方案 B「里程表」**）

原型见 `docs/更新弹窗-B.html`（独立精修版，含四种状态可切换）。
并列对比见 `docs/更新弹窗-对比.html`。

**结构（自上而下）**：

```
┌─────────────────────────────────────────┐
│              9:41  ·· ▮                  │
│                                         │
│  ┌──┐┌──┐  →  ┌──┐┌──┐                 │  ← 里程表：m19 → m20
│  │1 ││9 │     │2 ││0 │                 │     逐位向上滚，新位主色
│  └──┘└──┘     └──┘└──┘                 │
│  BUILD 200        BUILD 201             │  ← 等宽小字，左右对齐表盘
│                                         │
│           该翻表了                       │  ← 标题，对应"版本翻篇"
│       0.2.0+m19 → 0.2.0+m20             │
│  ────────────────────────────────       │
│  · 地图属性共建、自定义课程              │
│  · 2023 级培养方案、账页主题、调试日志    │  ← 可滚动区
│  · 修好：教师搜索崩溃、空闲教室、登录态   │
│  · 修好：地图拖动回弹                    │
│  ────────────────────────────────       │
│        [    立即更新    ]                │  ← 主色实心，独占一行
│   [  我知道了  ]  [  不再提醒  ]         │  ← 同行等分，描边
│           5.31 MB                       │
└─────────────────────────────────────────┘
```

**关键实现点**：

1. **里程表是唯一动效焦点**：数字位向上滚动（200 → 201），滚到位停住，**不循环**。
   项目原本只允许底部导航条一处动效，本方案新增第二处——
   因它是「有新版本」这个事件本身的表达，不是装饰。
   动效时长建议 400–600ms，`tween`，**无回弹**（与项目既有 180ms 导航条同族）。
2. **不是所有位都滚**：`200 → 201` 只有最后一位变，就只滚最后一位；
   只变一位时若整排都滚会显得假。**据此实现：逐位比较，只滚有变化的位**。
3. **本方案不用 `AlertDialog`**，用 `Box` + 底部 sheet（`Modifier.align(BottomCenter)`），
   因为要可滚动主体 + 固定页脚。`FeedScreen.kt` 的 `SheetScaffold` 可参考。
4. **顶部不写"发现新版本"这类标题**——标题就是「该翻表了」，
   版本号本身在表盘上。与主人「不重复标题」的一贯要求一致。
5. **条目列表用 `·` 前缀**（不是编号）——因为方案 B 的视觉重心在表盘，
   列表是次要信息，编号会抢戏。⚠️ 这与 2.2 第 1 条冲突，**以本节为准**：
   编号改前缀，切分规则不变。
6. **可滚动主体**：`verticalScroll` + `weight(1f)`，页脚固定。
7. **只显示包体大小，不显示预计时间**（网络波动大，写死会变假信息）。

**token 用法**：

- 表盘数字用 `NumericFont`（等宽），27–34sp；`BUILD 200/201` 等宽 9.5sp
- 主色 `t.primary`（农械橘 `#C74E17`）用于变化位的数字、主按钮
- 未变化的位用 `t.inkSoft`/`n300` 级灰——**新旧对比就是"翻表"的视觉语义**
- ⚠️ **AGENTS.md 已声明前端设计纪律全部作废**（2026-11-15），所以**不要**为这个弹窗
  新增 shape/颜色强制测试，也不要在文档里写"必须 0 圆角"之类的红线。
  沿用 `InkTokens` 现有取色即可，但**不得引入新的设计约束**。
- 触区 ≥48dp、条目文字 ≥11.5sp（可读性下限，不是设计纪律）。

## 3. 实现方案

### 3.1 数据层：加一个可观察信号

`UpdateCenter.kt` 的 `companion object` 里加进程级状态：

```kotlin
private val _available = MutableStateFlow<UpdateInfo?>(null)
val available: StateFlow<UpdateInfo?> = _available.asStateFlow()
```

- `check()` 返回 `CheckResult.Available` 时同时 `_available.value = info`
- 返回 `Latest` / 失败时 `_available.value = null`
- **用 `StateFlow` 不用 `SharedFlow`**：UI 可能晚于检查完成才订阅（检查在 Application 里跑，
  UI 要等首帧）。`SharedFlow` 会丢掉这个早到的事件。

### 3.2 偏好：记「不再提醒」的版本号

`UpdateCenter` 现有的 `prefs`（`SharedPreferences("update")`）里加一个键：

```kotlin
private const val KEY_DISMISSED_CODE = "dismissedCode"
```

- 读：`fun dismissedCode(): Long = prefs.getLong(KEY_DISMISSED_CODE, 0L)`
- 写：`fun dismissVersion(code: Long) { prefs.edit().putLong(KEY_DISMISSED_CODE, code).apply() }`

**不需要新文件、不需要迁移**。

### 3.3 UI 层：`EnRouteRoot` 里挂弹窗

在 `EnRouteRoot`（`EnRouteRoot.kt:66`）内部：

```
val available by UpdateCenter.available.collectAsStateWithLifecycle()
var showDialog by remember { mutableStateOf(false) }

LaunchedEffect(available, /* 加载完成信号 */) {
    val info = available ?: return@LaunchedEffect
    if (info.versionCode == dismissedCode) return@LaunchedEffect
    // 等加载完成：与其他弹层互斥 + 首帧后延迟
    delay(FIRST_FRAME_SETTLE_MS)          // 建议 500ms
    if (anyOtherOverlayVisible) return@LaunchedEffect
    showDialog = true
}

if (showDialog) UpdateDialog(...)
```

**互斥检查**：`EnRouteRoot` 里目前没有集中的"有无弹层"状态。两个办法：
- 简单：在 `EnRouteRoot` 用局部 `var` 记录本屏弹层（但子页面弹层它看不到）
- 更稳：先只在 **tab == 0（课表）且无 `CourseDetailOverlay`** 时弹——课表页是启动默认页，
  这已覆盖绝大多数场景
  
> 建议先用简单办法，并在计划里注明这是**已知限制**（如果用户恰好在资讯页打开了一个
> 详情浮层时启动，可能叠层）。后续若真的撞上，再抽全局 overlay 计数。

### 3.4 「立即更新」的跳转

需要从 `EnRouteRoot` 切到「我的」tab 并打开设置页的更新区块。
检查现有导航结构：`tab` 是 `mutableIntStateOf(0)`，`UserScreen` 内部有自己的 `stack`。

两个可行做法：

- **A（推荐）**：把「我的」tab 设为 `2`，同时给 `UserScreen` 一个可外部传入的初始页参数
  （或在 `UserScreen` 里读一个"请求跳到更新区块"的信号）。
- **B**：弹窗里**直接做下载**，不跳设置页——在弹窗内显示进度条（复用 `UpdateCenter.download`）。

> **B 的体验更好**（少一次跳转），但改动更大（要在对话框里复刻 `UpdateSection` 的状态机）。
> **建议本轮做 A**，先保证"能提醒、能说清内容、能跳过去"，进度条留在设置页。

## 5. 验收标准

| 项 | 要求 |
|---|---|
| 编译 | `compile-check.bat` 通过 |
| 单测 | 既有单测全绿（当前 440 条，见 README） |
| 新增单测 | ≥5 条，见下 |
| 启动不挡首帧 | `am start -W` 冷启动耗时与改动前（中位数 272ms）差异 < 30ms |
| 弹窗时机 | 冷启动后可见主界面，再弹窗；**不是白屏上弹** |
| 频率语义 | 「我知道了」→ 杀进程重进仍弹；「不再提醒」→ 不再弹 |
| 版本变化 | 服务器发更高版本后，之前被"不再提醒"的 `versionCode` 不影响新的 |
| 更新内容 | `notes` 按 `；` 分行、`·` 前缀；`、` 不切分；为空时整块不显示 |
| 表盘 | 逐位比较，**只滚有变化的位**；`200→201` 只滚最后一位；不循环 |
| 按钮布局 | 「立即更新」独占一行主色实心；「我知道了 / 不再提醒」同行等分描边（方案 B，见 1.5） |
| 三个按钮 | 各自行为符合 1.4 |
| 强制更新 | `isMandatory` 时**整块移除**「不再提醒」，其余两个按钮仍可用 |
| 长内容 | `notes` 有 20 条时主体可滚动、页脚不动、不撑破屏幕 |
| 动效 | 表盘滚动 400–600ms、无回弹；`prefers-reduced-motion` 等价开关下应直接跳到位 |

### 新增单测（JVM）

1. **频率判定**：`shouldShow(info, dismissedCode)` —— 同版本 dismissed → false；不同版本 → true。
2. **notes 切分**：`parseNotes("a；b、c\nd")` 得到 3 条（`、` 不切分）；空串返回空列表。
3. **notes 截断**：超过 8 条时返回前 8 条 + 剩余计数；正好 8 条不显示计数。
4. **强制更新不显示"不再提醒"**：`isMandatory == true` 时 UI 决策函数返回 false。
5. **dismiss 只压该版本**：`dismissVersion(200)` 后，`shouldShow(201)` 仍为 true。
6. **编号格式**：`parseNotes` 产出的序号是补零两位（`01`…`08`），超过 9 条时 `10` 不补零出错。

> 第 1–6 条建议抽成 `UpdateDialogPolicy` 纯函数（新小文件或放 `UpdateManifest.kt`），
> 便于单测，也避免 UI 里散落判断。

## 7. 建议执行顺序

```
① 纯函数（shouldShow / parseNotes）+ 单测      ← 零风险，先绿
② UpdateCenter 加 StateFlow + dismissedCode    ← 数据层，不影响 UI
③ UpdateDialog 组件（可先固定假数据预览）
④ EnRouteRoot 挂载 + 互斥 + 延迟
⑤ 「立即更新」跳转或内嵌下载（方案 A）
⑥ 真机验收三种频率语义
```

> 那个动 `FeedRepository`/`FeedHttp`，这个动 `UpdateCenter`/`EnRouteRoot`，
> 混在一起出问题难定位，且都会碰到"启动路径"。
