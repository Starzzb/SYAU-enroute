## 2. 版本号规则

`app/build.gradle.kts:33-34`：

```kotlin
versionCode = 410          // 单调递增；用户端靠它判断「是不是更新」
versionName = "0.8.1+m33"  // 展示用；+mNN 是开发批次
```

发版时两块都要改，**versionCode 只能加不能减**（装低版本报 `INSTALL_FAILED_VERSION_DOWNGRADE`）。

**当前序号锚点**：m32 因换签名断代跳到 `400`，之后按 `400 + (NN-32)×10` 递增：
m32=400、m33=410、m34=420、m35=430…… 发版取整十，开发版取 `+1…+9`。

## 2.1 两套号：发布版与开发版分开（2026-11-17，主人指令）

原话：「开发版本号的管理也应该另外设置一套约定」。此前发布版和开发版共用一套号，
结果出现两种混乱：同一版本号既有「发过 Release 的包」又有「本机还在改的包」；
批次号（`mNN`）既是里程碑又被当成补丁号用。

从 m27 起分成两条线，**互不占用对方的号**：

| | 发布版 | 开发版 |
|---|---|---|
| 何时用 | 打 tag、发 GitHub Release、能装到别人手机上 | 只在本机／备用机迭代，随时被覆盖 |
| `versionName` | `0.<minor>.<patch>+m<NN>` | `0.<minor>.<patch>-dev.<n>` |
| `versionCode` | `(NN + 1) × 10`，m32 后按 `400+(NN-32)×10` | 发布版号 `+n`（`n` = 1…9，同批次内自增） |
| 标签 | `mNN` | 不打标签 |
| 落盘 | 同步 `releases/latest.json`、`CHANGELOG.md` | 什么都不写 |

规矩：

1. **一个批次号只发一次**。发出去就是那个号，之后同批次改动一律走开发版号；
   真要发布就开新批次。坏包删 tag 后重发**沿用原号**，不许拿旧号发新内容。
2. **`versionCode` 必须严格递增**，开发版 `+n` 一定大于同批次发布版，
   装回发布版时要么同号覆盖（`-r`），要么用下一批次 —— 不要为了「干净」把号码调小。
3. **`versionName` 里不写日期、不写功能名**：`+mNN` 已经能对上 `CHANGELOG.md` 的一节。
4. Release 标题格式固定 `mNN · 0.x.y+mNN`；说明一句话，详见 `CHANGELOG.md`（AGENTS.md）。

## 2.2 1.0 的门槛（2026-11-17，主人指令）

原话：「在功能完善自洽之前，不要升级到 1.0 版本」。`minor` 可以走（0.6 → 0.7 …），
但 **`1.0.0` 必须同时满足下面全部条件**才允许改：

- [ ] 课表 / 成绩 / 考试 / 资讯 / 地图 / 我的 / 设置 七条主链路都能在**没登录**、会话过期、断网、非校园网四种状态下给出正确且不互相矛盾的提示
- [ ] 「暂缺」只出现在真的取不到的地方，没有为了凑数补的假值（数据诚实）
- [ ] 更新链路自己走通：检查 → 下载 → 校验 → 拉起权限 → 装完自动回到前台
- [ ] 没有占位票（`票 NN`）、没有「开发中」字样、没有指向不存在功能的入口
- [ ] 接口诊断 14 条在校园网内全绿；失败时能给出一句真原因
- [ ] 界面里不存在说明书式文字（AGENTS.md「用设计，不用文字」）
- [ ] 至少一台非开发者手机连续使用一周，无崩溃、无数据错乱

不满足就继续留在 `0.x`。这条不设期限。

## 4. 更新分发链路（**核心，2026-11-20 按代码重写**）

**两条独立链路，缺一不可。** 先回答最常见的疑问：

> 我本地 commit + push 之后，用户读到的是**上游仓库**的 `releases/latest.json`；
> 用户端再按 json 里 `url` 指定的 GitHub Releases 地址下载 APK。两个地方都要更新。

```
本地 releases/latest.json ──git push──▶ GitHub 仓库 master 分支 releases/latest.json
                                              │
                                     清单镜像（5 条按序试）
                                              ▼
                                          用户端 App
                                              │ 解析 url（必须是本仓库 Releases 前缀）
                                              ▼
本地 APK ──gh release create──▶ GitHub Release 资产 ──下载镜像──▶ 用户端校验 sha256 ──▶ 安装器
```

### 4.1 清单源（latest.json）：仓库 raw + 镜像

代码在 `app/src/main/java/cn/dkarbon/enroute/data/UpdateCenter.kt:412` 的 `MANIFEST_URLS`，按顺序试，第一个拿到就用：

| 顺序 | 地址（都指向 `Starzzb/SYAU-enroute/master/releases/latest.json`） | 实测 |
|---|---|---|
| ① 主 | `https://gh-proxy.com/https://raw.githubusercontent.com/...` | 832ms，**内容最新** |
| ② | `https://raw.githubusercontent.com/...` | 669ms，国内时通时断 |
| ③ | `https://raw.githack.com/...` | 904ms，**会缓存旧版** |
| ④⑤ | `https://cdn.jsdelivr.net/gh/...@master/...` / `fastly.jsdelivr.net/...` | 最快（428–656ms），但分支缓存 **12 小时** |

**自建机不用**：`47.95.12.198:18081/app/latest.json` 返回 404、`:18082` 连接被掐，`/app/` nginx 路由从未配置，代码注释里已标「现不可用」。

**CDN 缓存对策**：`UpdateCenter.cacheBusted()` 给清单 URL 加 `?t=yyyyMMddHH`（按小时），
配合请求头 `Cache-Control: no-cache, no-store`，保证改完 latest.json 立刻能查到。
只读清单加时间戳，**不加到 APK 下载地址**（会让 sha256 校验的缓存优势归零）。

### 4.2 APK 源：只能 GitHub Releases（代码钉死）

`app/src/main/java/cn/dkarbon/enroute/data/UpdateManifest.kt:111`：

```kotlin
const val PINNED_RELEASE_PREFIX = "https://github.com/Starzzb/SYAU-enroute/releases/download/"
```

`latest.json` 的 `url` **必须以此开头**，且 https + 主机在白名单（`github.com`、`objects.githubusercontent.com`、`release-assets.githubusercontent.com`、`github-releases.githubusercontent.com`）。
指到网盘、自建服务器、别的仓库 → App 直接报「下载地址不在允许的范围内」并拒绝更新（故意的：宁可拒绝，不可装错）。

**下载加速**：`MIRROR_PREFIXES = ["https://gh-proxy.com/", "https://ghproxy.net/"]`，
由 `mirrorsOf()` 从**已通过校验的**入口地址拼出来，**直连优先、失败再走镜像**。
镜像只做下载、不做清单源。GitHub 302 跳到 `objects.githubusercontent.com` 属正常，逐跳校验主机白名单放行。

### 4.3 为什么 APK 不放服务器

早期服务器出口带宽实测约 **148 KB/s（≈1.2 Mbps）**，4.75 MB 包要 30 秒还挤占地图补丁 API。
所以服务器不承担 APK 分发；release 包经 R8 混淆 + 资源优化约 8.5 MB（m32），走 GitHub Releases 由 CDN 承载。
（旧文档「网盘直发」「`/var/www/app/` 放 APK」已废弃。）

## 5. 应用内「检查更新」（**已实现，非待办**）

`app/src/main/java/cn/dkarbon/enroute/data/UpdateCenter.kt` + `UpdateManifest.kt` + `UpdateInstall`：

- **触发**：设置页手动「检查更新」；`EnRouteApp.kt` 启动时**每天最多静默检查 1 次**（只提示不打扰）
- **流程**：GET 清单（§4.1）→ 解析校验字段 → 比 `versionCode` → 有新版弹动作条 → 用户点了才下载（§4.2）→ 校验 sha256 → 拉起安装器
- **字段校验**（`UpdateParse.latest`）：versionCode 正整数、versionName/url 非空、url 过前缀白名单、sha256 必须 64 位十六进制 —— 任一项不合格整体失败，不猜、不降级成「有更新」
- **安装**（`UpdateInstall`）：没有「安装未知应用」权限 → 先跳系统设置页（数据 URI 只认 `package:cn.dkarbon.enroute`）；有权限 → 交系统安装器。不静默安装、不后台自动下大包
- **notes**：`latest.json` 的 `notes` 只写一句话，弹窗空间有限；详细改动进 Release 正文与 `CHANGELOG.md`

## 6. 手动发版的 8 步清单

1. **定版本号**：改 `app/build.gradle.kts:33-34`，按 §2 的锚点取新号（例：m34 发版 → `420` / `0.8.2+m34`），只增不减。

2. **全测 + 打包**：
   ```powershell
   cd O:\dev\enroute-android
   cmd.exe /c build-test.bat     # 日志 build-log.txt 是 GBK，用 Get-Content -Encoding Default 读
   cmd.exe /c build-release.bat  # → app\build\outputs\apk\release\app-release.apk
   ```
   成败只看日志末尾 `BUILD SUCCESSFUL` + `EXIT=0`，**别信 `$LASTEXITCODE`**（管道末端命令会骗人）。

3. **真机冒烟**：装 release 包跑关键路径（课表 / 资讯 / 大纲 / 地图 / 我的 / 设置）。装包必须用 release 签名，禁卸载清数据；见 AGENTS.md。

4. **算 APK 的 sha256 和 size**：
   ```powershell
   certutil -hashfile app\build\outputs\apk\release\app-release.apk SHA256
   (Get-Item app\build\outputs\apk\release\app-release.apk).Length
   ```

5. **改 `releases/latest.json`** 六字段：`versionCode`、`versionName`、`url`、`sha256`、`size`、`notes`。
   `url` 写成 `https://github.com/Starzzb/SYAU-enroute/releases/download/mNN/SYAU-enroute-mNN.apk`（前缀见 §4.2）；
   `notes` 一句话。把 APK 复制成 `releases/SYAU-enroute-mNN.apk` 备存。

6. **生成 Release 正文**：
   ```powershell
   powershell -ExecutionPolicy Bypass -File tools\release-notes.ps1 -Tag mNN
   ```
   脚本自动 `git describe` 取上一 tag、拼提交标题 + CHANGELOG 小节，落 `.tmp/release-notes-mNN.md`，并打印 `gh release create` 命令（不执行）。

7. **提交 → 打 tag → push（带代理）**：
   ```powershell
   git add -A
   git commit -m "release: mNN ..."
   git tag -a mNN -m "..."
   git -c http.proxy=http://127.0.0.1:7890 -c https.proxy=http://127.0.0.1:7890 push
   git -c http.proxy=http://127.0.0.1:7890 -c https.proxy=http://127.0.0.1:7890 push origin --tags
   ```
   **push 之后用户端才能读到新 `latest.json`** —— 只改本地不 push，用户永远看不到。

8. **传 APK 到 GitHub Release**（`url` 里写的那条）：
   ```powershell
   gh release create mNN releases\SYAU-enroute-mNN.apk --title "mNN · 0.x.y+mNN" --notes-file .tmp\release-notes-mNN.md
   ```
   没有 APK 的 Release，清单指过去会 404。最后内测群发一句「已更新到 mNN」。

## 7. 回滚

- GitHub Release **保留上一版 APK**，出问题就把 `releases/latest.json` 的 `url`/`sha256`/`versionCode` 改回旧版并 push
- 但 `versionCode` 不能降级 → 回滚要**把旧代码重新打一个更大 versionCode 的包**（`git checkout <旧tag>` → 改号 → 重新打包走 §6）
- 别删 tag，那是唯一可靠的「回到某个可用状态」的锚点
