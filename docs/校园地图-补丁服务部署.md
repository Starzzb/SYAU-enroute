## 3. 接口

> ⚠️ **本节以 `tools/map/server.js` 的实现为准**（2026-11-14 逐行核对过一遍）。
> 之前这几条写错了：`featureId` 正则、`reasons` 的形状、"按主键去重（幂等）"。
> 另外 **2026-11-14 新增了拉取接口** —— 早期版本写「没有 `GET` 接口、只能单向上报」，
> 那句话已作废：现在是**服务端为基准 + 增量拉取**（`GET /map/api/dataset`），见下。

### POST /map/api/patches
```jsonc
{
  "schema": 1,
  "mapVersion": "2026.11.14-1",
  "client": { "did": "anon-<本地随机UUID>", "appVer": "0.3.0+m20" },
  "patches": [
    { "featureId": "f19", "field": "层数", "value": "3", "op": "set", "ts": "2026-11-14T15:40:00+08:00" }
  ]
}
```
- 头：`X-Api-Key: <CMAP_API_KEY>`（**服务端配了才校验**；缺失/不符 → 403）
- 单次 **≤200 条**、body **≤256KB**；单值 **≤200 字**
- `featureId` 必须 **`^f\d{1,6}$`** —— ⚠️ **不接受 `f0_1` 这种带下标的兜底 id**
  （`pack.py` 在没有 UID 时会生成它；那批数据上传会被整条拒绝，客户端现已在上传前预检并提示）
- `field`：非空、**≤20 字**、**没有白名单**（`name` / `kind` 也允许，它们就是固定字段名）
- `op` ∈ `set | delete | addField`；`mapVersion` 必须形如 `2026.11.14-1`
- 返回：`{accepted, rejected, reasons: [ {featureId, field, reasons:[…]} ], keys}`
  —— ⚠️ **`reasons` 是数组**（每项带自己的 `reasons` 子数组），不是 map
- 限流：每个贡献者（`ch`）**400 条/小时**

#### ⚠️ 去重/幂等：**服务端不做**
`id = sha1(mv|fid|field|value|ch|now)`，其中 `now` 是**服务器接收时间** ——
所以同一批数据**重复提交会新增记录**，不会去重。
- 生效值靠 `(mv,fid,field)` 索引 + **按 `ts` 取最新**兜底
- **去重责任在客户端**：上传成功即出队、同一格只留最新一条（`data/map/MapContributeStore`）

### GET /map/api/dataset?mapVersion=&since=
**返回聚合后的生效数据，不是补丁流。** 只读、匿名，不需要 admin key。

```jsonc
{
  "schema": 1,
  "mapVersion": "2026.11.14-1",
  "rev": 42,                       // 每次落盘自增，持久化在 DATA_DIR/rev.txt
  "since": 0,
  "incremental": false,            // since>0 且请求了增量时为 true
  "updatedAt": "2026-11-14T19:20:00+08:00",
  "fields": ["层数", "所属单位"],
  "features": { "f19": { "层数": "3", "所属单位": "体育部" } },
  "deleted": [ { "featureId": "...", "field": "..." } ],
  "fieldRev": { "f19": { "层数": 1, "所属单位": 2 } }
}
```

- **`rev` 是数据版本，不是审核标记** —— 与 `approved` 必须分开（曾混用，导致未审补丁被
  `snapshot` 当成已审核吐出去）
- `since=<rev>` 时只返回「被 `rev>since` 的记录碰过的格」的**当前生效值**。
  这样即使某条补丁因 `ts` 旧而落选，客户端也不会漏掉该格的最新值；客户端不必复刻服务端聚合规则
- `ETag: "<mapVersion>-<rev>"` + `If-None-Match` → **304 空 body**（真零流量）
- 空库返回 `{"rev":0,"features":{},"fields":[]}`，客户端**必须当成合法响应**（不是解析失败），
  全部字段回落内置 asset

**聚合口径**（服务端负责，客户端不重复实现）：同 `(mapVersion, featureId, field)` 取 `ts` 最新；
`op=delete` 进 `deleted` 并从 `features` 消失；`addField` 只贡献字段名与值。

### GET /map/api/stats
`{patches, effectiveKeys, features, fields, rev, updatedAt, versions}` —— 排查用。

### POST /map/api/approve
需 `X-Admin-Key`（与 snapshot 同一把）。`{"ids":[...]}` →
`{approved, missing:[...], alreadyApproved}`。

- **只能 0→1，没有反审路径**（要撤另做端点）
- 幂等：重复 approve 同一批 → `approved:0, alreadyApproved:N`
- 找不到的 id 原样进 `missing`，**不静默跳过**
- 审核结果追加到 `DATA_DIR/approved.jsonl` —— 不碰 `patches.jsonl`（那是只追加的审计日志，改写等于毁证据）

### ⚠️ nginx 有 UA 过滤器，手工验证必须带 App UA

```
if ($http_user_agent ~* "(curl/|wget/|python-|...|java/|...)") { return 403; }
```

用 `curl` 默认 UA 测会拿到 **403**，看起来像权限问题其实是 UA。
`HttpURLConnection` 默认 UA 是 `Java/1.x`，**正好命中黑名单** ——
客户端两个类（`MapUploader` / `MapDatasetClient`）的 `UA` 常量不能删。

```bash
curl -A "SYAU-Enroute-Test" http://127.0.0.1:18082/map/api/health   # 200
curl                          http://127.0.0.1:18082/map/api/health   # 403（设计如此）
```

### GET /map/api/snapshot?mv=<版本>
需 `X-Admin-Key`。只返回 `approved=1`（已人工审核）的合并结果，
且**每格取最新的已审记录**（未审的新值不会顶掉已审值）：
`{mapVersion, fields:[…], features:{"f19":{"层数":"3"}}}`

### GET /map/api/health
`{ok, keys, ts}` —— keys 是内存里生效的 (mv,fid,field) 条数。

## 4. 身份与可追溯性

**2026-11-14 起：App 明确发送机型与设备标识（主人决定）。**

`client` 块现在带 `manufacturer / model / device / sdkInt / release / ssaid / installId`
（+ `did` / `appVer`）。这与早期「不发送 model」的写法**相反**，
因为主人明确要求收集上传者信息用于用户画像识别，并接受这个取舍。

能做到的与做不到的（别在文档里写"采集 IMEI"这种做不到的承诺）：

| 字段 | 来源 | 说明 |
|---|---|---|
| `manufacturer` / `model` / `device` | `Build.*` | 如 `vivo` / `V2301A` / `PD2301` |
| `sdkInt` / `release` | `Build.VERSION.*` | 取不到时**不发这个键**（不写 0） |
| `ssaid` | `Settings.Secure.ANDROID_ID` | **按「应用+签名+用户」派生，不是真硬件号**。取不到或为 `unknown`/全零/超长时发**空串** |
| `installId` | 本地 UUID | 卸载重装会变；「重置身份」一并更换 |

⚠️ **IMEI / 序列号在 Android 10+ 对普通应用完全不可读**（`READ_PHONE_STATE` 也不行）。

**唯一的隐私闸门是开关**：`MapContribute.shouldSend(enabled, patches)` 是 `upload()` 第一行的判定，
关着开关连队列都不读。首次开启要过一道确认弹窗，逐项列出「会传这些 / 不会传这些」。

**`sid`（学号）仍然不发送** —— 代码里没有任何路径能把它带出去。
下表里 `sid_enc` 在本项目实际数据里恒为 `null`。

服务端只落派生值，**明文身份一个字节都不存**：

| 字段 | 算法 | 用途 |
|---|---|---|
| `ch` | `HMAC-SHA256(CMAP_SECRET, sid\|did)` | 判断「是不是同一个人」、限流、聚合贡献 |
| `sid_enc` | `AES-256-GCM(CMAP_SECRET, sid)`，带 `v1:` 前缀与随机 IV | **只有持 CMAP_SECRET 才能解回学号** → 可追溯 |
| `did_h` | `HMAC-SHA256(CMAP_SECRET, "did\|"+did)` 前 16 位 | 同设备归并，不可反推 |

**实测验证**：提交带 `sid=SELFTEST-SID`、`did=probe-device-aaa` 的补丁后，
`grep -c 'SELFTEST-SID' patches.jsonl` 与 `grep -c 'probe-device-aaa'` **均为 0**。

**反查某个学号的记录**（只有服务器上能跑）：
```bash
cd /opt/campusmap/api
set -a; . ./env; set +a
# 用 sid 与疑似 did 组合算 ch，再到 jsonl 里 grep
python3 - <<'PY'
import hmac,hashlib,os
sec=os.environ['CMAP_SECRET'].encode()
for sid,did in [("2024xxxxxx","<设备UUID>")]:
    print(hmac.new(sec,f"{sid}|{did}".encode(),hashlib.sha256).hexdigest())
PY
```

## 7. 数据怎么进产品（两条链路，各管一件事）

### 链路 A：共享数据集（实时，服务器为基准）

```
客户端（默认关）—手动点「立即上传」→ POST /map/api/patches
        ↓
服务端聚合（(mv,fid,field) 取 ts 最新）→ rev 自增
        ↓
其他客户端 GET /map/api/dataset?since=<本地 rev> → 标「共建」
```

显示优先级三档（`MapDataset.rows`）：

```
① 本地待传（可编辑，只在你自己机器上）  ← 最高
② 服务器共享数据（只读，标「共建」）    ← 基准
③ 内置 asset（只读，标「内置」）        ← 兜底
```

「以服务器为基准」成立：别人的数据、以及你上传成功后的数据都以服务器为准。
规则 ① 存在的唯一理由是**别吃掉用户刚填、还没传上去的东西**。

### 链路 B：进安装包（人工审核，仍是红线）

```
patches.jsonl → merge_edits.py（幂等 + 不动点有单测）→ conflicts.txt 人工过一眼
        ↓
POST /map/api/approve（admin key，把通过的 id 置 approved=1）
        ↓
tools/map/pack.py --from-geojson → assets/map/campus.geojson + manifest.customFields
        ↓（随版本发布）
用户更新 App → 官方基线作为只读层出现（标「内置」，不计入「已标注 N」）
```

**两条链路不冲突**：A 让数据用得起来，B 是「写进安装包」的稳定基线。
`snapshot` 只吐 `approved=1` 的记录，且**每格取最新的已审记录** ——
未审的新值不会顶掉已审值（否则审核结果会凭空消失）。

## 10. 2026-11-27：审核闸门真的加上了 + 审核页

### 之前是假的

`aggregate(mv, sinceRev)` 原来直接遍历 `index`（每格 ts 最新那条），**全程不看 `r.approved`** ——
未审补丁会顶掉已审值，直接进 `GET /map/api/dataset` 发给所有客户端。只有 `/map/api/snapshot`
（写安装包那条链路）过滤 approved。也就是说「人工审核」这道门只挡了发布，没挡线上共享数据。

改法：新增 `approvedBest()`，遍历 `records` 只认 `r.approved === 1`，每格取 ts 最新；
`aggregate` 与增量分支（`r.rev > sinceRev`）都改成只收已审。`rev` 照旧自增 ——
**补丁进来了、rev 前进、但内容不变**，客户端不会因为「有新版本」而白拉一次内容。

### 现在怎么审

| 项 | 值 |
|---|---|
| 审核页（首选） | `https://wb.dkarbon.cn/map/admin/`（同域名 TLS，2026-11-27 加） |
| 审核页（明文备用） | `http://47.95.12.198:18082/map/admin/`（手机链路口，仅供人手动打开） |
| basic auth 用户 | `admin`（口令在 `/etc/campusmap-admin.env`，600） |
| 页面里还要填的钥匙 | `CMAP_ADMIN_KEY`（在 `/opt/campusmap/api/env`，600） |
| 两个新接口 | `GET /map/api/pending?limit=200`、`POST /map/api/approve`（均要 `X-Admin-Key`） |
| 统计接口 | `GET /map/api/stats` 现在也要 `X-Admin-Key`（以前谁都能看） |

页面只做一件事：列待审 → 勾选 → 通过。没有驳回，没有撤销 —— 撤销要另开接口，
免得一个口既能审又能撤，出事查不清是谁。

### 上线过程里踩到的三件事

1. **旧单元抢端口**：老的 `campusmap.service`（8 天前起的）一直占着 7870，新的
   `campusmap-api.service` 起来就 EADDRINUSE 反复重启 —— 而 7870 上仍是旧代码，
   表现为「部署成功、health 正常、审核闸门没生效」。`deploy.sh` 现在会先 stop + disable 老单元。
2. **自检的 curl 被自己的 UA 过滤器挡住**：18082 拒 `curl/` UA，所以「带钥匙应 200」那条
   自检一直是 403，看着像钥匙错。自检现在统一带 `-A "SYAU-Enroute/0.0.0-deploy-check"`。
3. **闸门一上，线上数据立刻全空**：26 条补丁里 approved 是 0 —— 以前显示的都是没审过的。
   这是**诚实的空**，不是故障；要恢复显示就由主人在审核页逐条过。
