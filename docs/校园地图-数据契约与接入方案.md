## 0. 一句话回答「一个 SHP 够不够」

**不够，而且技术上不可能只用一个。** 四个硬原因：

1. **Shapefile 不是单文件**：`.shp`（几何）+ `.shx`（索引）+ `.dbf`（属性）是必需三件套，
   缺一个就打不开；`.prj`（坐标系）和 `.cpg`（编码）强烈建议一起带。
   你现在的草稿就缺 `.prj`（我实测过）。
2. **一个 shapefile 只能存一种几何类型**（点 / 线 / 面三选一）—— 也就是说**点要素不能混进面图层**。
   但注意：**POI 可以画成「面状符号」**（一个小方块/圆点面），这样它就能进面图层。
   所以 v1 允许「一个面图层装全部」，见 §1 的修订。
3. **一个 shapefile 只有一张属性表**。建筑要「楼号/层数/所属单位」，POI 要「子类/开放时间」，
   字段结构完全不同，硬塞一张表会一半字段永远为空。
4. 字段名 ≤ 10 个字符、DBF 编码默认 GBK（中文易乱、跨平台易炸）。

→ **结论：按图层拆分，最少 2 个（building + poi），推荐 4~5 个。**

## 1. 图层方案：**一个面图层装全部也行**（v1 就这么干）

主人拍板：**第一版只做相对位置地图**（无 GPS、不申请定位权限），校园地标**都用面**表示。
这是合法的：面图层有属性表，POI 画成「面状符号」（小方块/小圆面）即可，用 `kind` 区分。

### 两种交付形态，都支持

| 形态 | 做法 | 适用 |
|---|---|---|
| **A. 单文件（v1 推荐）** | 一个 `campus.shp`（Polygon），属性表字段取**并集**，`kind` 区分建筑/绿地/水面/道路/POI符号 | 图不大、你一个人画、想省事 |
| **B. 多文件（将来）** | `building.shp` + `poi.shp` + …，各表各自精简 | 要素上千、多人分工、需要分别维护 |

**App 端不关心是单文件还是多文件** —— 契约里 `manifest.layers[]` 是**逻辑层**，
每个逻辑层可以指向同一个 geojson 并按 `kind` 过滤：

```jsonc
"layers": [
  {"name":"building", "file":"campus.geojson", "filter":{"kind":["teach","dorm","lab","office","gym","hall","library","hospital"]}},
  {"name":"green",    "file":"campus.geojson", "filter":{"kind":["green"]}},
  {"name":"water",    "file":"campus.geojson", "filter":{"kind":["water"]}},
  {"name":"poi",      "file":"campus.geojson", "filter":{"kind":["gate","food","wc","park","bus","canteen"]}}
]
```
→ 你交一个文件，我拆成 4 个逻辑层渲染；将来你拆成多文件，**只改 manifest，App 代码不动**。

### 单文件形态的三个代价（接受就单文件）

1. **字段并集会有空列**：建筑的 `floors`、POI 的 `open` 互相为空 —— App 端已按「空就不显示这一行」处理，不影响观感
2. **面状符号不随缩放保持大小**：缩小后校门那个小方块会变得很小、点不准 → App 端给**最小触控半径（≥24dp）**兜底
3. **画 POI 面时别画太小**：建议**等效直径 ≥ 场景尺度的 0.3%**（1024 宽的图上约 ≥3px），否则你自己在 QGIS 里都点不中

## 3.5 底图：**原图当底 + 矢量当交互层（v1 采用）**

主人问「SHP 是当顶层交互层铺在真实地图上，还是直接出图」。看过源资料后结论明确：

**源文件 `校园底图_像素坐标.tif`（1024×648）本身就是一张成品示意图** ——
有标题「沈阳农业大学核心校区平面示意图」、右下角**图例（12 项）**、右上**指北针**、
山体（天柱山）/植物园/居民生活区/老操场/运动场跑道等细节与楼名标注。
**它不是卫星影像，不需要"真实地图"垫底。**

### 决策：双模式，默认「原图底 + 交互层」

| 模式 | 组成 | 何时用 |
|---|---|---|
| **B. 原图叠加（默认）** | 位图底图（原示意图）+ 416 面半透明热区 + 选中描边 | 日常浏览：信息量最全、最像"校园地图" |
| **A. 纯矢量（开关）** | 只用 416 面按 `kind` 上色自绘，无位图 | 高倍放大（位图糊了）、深色主题、将来重绘 |

关键优势：**底图与矢量层共享同一像素坐标系，天然像素级对齐，不需要任何地理配准**
（你的 `03_对齐校验.png` 就是干这个的）。这正是「顶层交互层」路线里**唯一不需要配准**的走法；
需要配准的只有「卫星影像 / 在线瓦片」那种，那条放 v3 以后（要 key、要网络、要授权、体积大，
且与 App 现有硬朗纸墨风格打架）。

### B 模式必须处理的三个实现点

1. **y 轴方向相反**：源数据说明写明「左下角原点，**y 轴向上**」，而屏幕 y 向下 →
   渲染时 `screenY = (bbox.maxY - y) * scale`，不做这步整图会被上下翻转。
2. **底图分辨率**：1024 宽在 3× 放大会糊。请**另出一张 2×（2048×1296）或更高**的底图
   （从原始 JPG 高分辨率版本直接栅格化，别拿 1024 放大插值）。
   建议同时给 `map/base@1x.webp` 与 `map/base@2x.webp`，App 按缩放级别选。
3. **放大时的策略**：缩放 > 2.5× 时把位图淡出（alpha 降到 0.35）或直接切 A 模式，
   避免糊成一片；矢量层始终清晰。

### 交互层样式

- 常态：`kind` 对应色、**填充 alpha 约 10~14%**（能看出分区但透出底图细节），不描边
- 选中：填充 alpha 40% + 2dp 描边 + 其余要素淡化
- 底图已含楼名文字，所以信息卡要提供**底图没有的东西**：层数、所属单位、备注、
  以及（后续）「这栋楼今天有什么课」—— 否则点开只是重复底图上的字，没有附加值

### 省力提示：`kind` 只需标 12 行，不是 416 行

你的图是「按 **12 个色组**聚类出的图块」，而原图图例也是 **12 项** —— 两者应为一一对应。
所以把 12 个 `色值` 与图例色块对上，就能自动填出全部 416 个要素的 `kind`，
**你只需要核对 12 行映射 + 补楼名**。这一步我可以做（比对色值 + 你确认图例文字）。
## 4. 坐标系：**v1 已定 —— 相对位置（local），不做 GPS**

主人拍板（2026-11-14）：**第一版只做相对位置地图**。因此：

- `manifest.crs = "local"`，`bbox = [0,0,1024,648]`（或你最终图幅的像素范围）

**App 代码不用改**（契约预留），只需重出地图包。

## 5. 插拔契约：地图包（Map Package）

你要的「可替换更新」，靠一个**带版本号的目录契约**实现，App 不重装就能换图。

```
map/
  manifest.json          ← 入口，App 先读它
  building.geojson
  poi.geojson
  base.geojson           ← 可选
```

`manifest.json`：

```jsonc
{
  "schema": 1,                    // 契约版本；App 校验，不匹配就回退内置
  "version": "2026.11.14-1",      // 你的版本号，界面上会显示
  "crs": "local",                 // "local"（像素/本地）或 "EPSG:4326"
  "bbox": [0, 0, 1024, 648],      // local: 源图像素范围；4326: [minLon,minLat,maxLon,maxLat]
  "origin": "校园规划图 1024x648", // 人类可读的来源说明
  "layers": [
    {"name": "building", "file": "building.geojson", "geom": "polygon",
     "label": "建筑", "fill": "#E7E3CD", "stroke": "#1A1611"},
    {"name": "poi", "file": "poi.geojson", "geom": "point",
     "label": "设施", "fill": "#C74E17"}
  ],
  "generated": "2026-11-14"
}
```

**App 读取顺序**
1. `filesDir/map/`（用户可替换：塞进去一个新目录即生效）
2. 回退 `assets/map/`（随包内置）
3. 校验失败（schema 不认 / 缺图层 / GeoJSON 解析失败 / bbox 与要素范围差太远）→ **回退内置并提示**，绝不白屏

**换图流程**：你把新 SHP 给我 → 我跑转换脚本 → 产出一个新的 `map/` 目录 → 你把它放进 App 的 `filesDir/map/`（或我打个新包内置）→ 打开即新图，**设置页会显示当前版本号与生成日期**。

## 7. App 端渲染方案（先 Canvas 自绘，不引地图库）

**为什么不用地图库**：这个 App 一贯不加依赖；而且校园地图**不需要底图瓦片**（自绘即可）、
不需要网络。用 Compose `Canvas` 就够：

- 读 GeoJSON → 按 `bbox` 做**等比映射**到画布（保持长宽比、留边）
- 手势：双指缩放（1×~8×）、单指拖拽、双击放大、边界回弹
- 命中测试：点选 → 点在多边形内（射线法）取最小面积者；点图层按屏幕距离取最近（≤24dp）
- 点中后：底部信息卡（名称 / 类别 / 楼号 / 层数 / 单位 / 备注 / 「这栋楼里有什么课」入口）
- 与课表打通（后续）：点建筑 → 显示该楼今天的课（教室号前缀能对上，如 `2-606` → 第二教学楼）
- 样式沿用现有硬朗体系（0 圆角、无渐变、描边分层），**颜色不写死**，从 manifest 的 `fill/stroke` 读

性能预算：416 个面 + 若干点，Path 缓存后拖动/缩放应稳 60fps；点选只对屏幕内的要素做命中测试。

## 9. 三种「替换」的边界（回答「底层矢量图之后能不能换」）

**能换，但要分清换的是什么**，三者耦合程度完全不同：

| 换什么 | 能不能换 | 前提条件 | 用户已录属性会怎样 |
|---|---|---|---|
| **属性**（名称/类别/自定义字段） | ✅ 随时 | 无 | 不受影响（存在 `edits.json`，与图纸解耦） |
| **底图位图**（`base@1x.webp`） | ✅ 随时 | 必须与矢量**同一像素坐标系、同画幅**（改了画幅就要改 `manifest.bbox`） | 不受影响 |
| **矢量几何**（重新矢量化/补块/改形状） | ✅ 能，但**有代价** | `id` 必须稳定 | **靠 `id` 关联**：id 变了属性就错位 |

### 几何换版时怎么不丢属性

`edits.json` 只存「`featureId` → 字段值」，所以：

1. **推荐做法**：重画时保留原 `ID`（你现在的 `ID` 字段就是稳定键，我映射成 `f19`）。
   补块/微调形状都不影响 id，属性自动跟着走。
2. **id 变了的话**（重新跑聚类就会变）→ 需要**迁移**，我出脚本按以下顺序匹配：
   - ① `id` 精确命中
   - ② 名称完全相同（`九州体育场` 这种唯一名很好用）
   - ③ 质心落在旧面内 / 面积重合率 > 0.6
   - 迁移不了的进「孤儿清单」，逐条问用户「这条『九州体育场·层数=3』要挂到哪个新块上」
3. **红线**：**绝不静默丢弃**。`manifest.version` 一变，App 顶部就提示「本次地图更新有 N 条标注待确认」。

> 所以结论：**图可以一直迭代**，但每次重画要尽量保住 `ID`。你重画前告我一声，我先把现有属性导出成一份 `edits_backup.json`。

## 10. 内测期众包完善属性（借服务器收数据）

定位：只补「某个块的属性」，数据量极小（90 个面 × 若干字段 ≈ 几 KB），
**不需要上传几何、不需要上传底图**，服务器只存补丁。

### 10.1 数据形态：补丁流，不是整包覆盖

```jsonc
// POST /map/patches   （批量，一次最多 200 条）
{
  "schema": 1,
  "mapVersion": "2026.11.14-1",
  "userKey": "anon-7f3a9c",          // 匿名设备键（随机生成、可重置），不含学号姓名
  "patches": [
    {"id":"sha1(f19|层数|3|anon-7f3a9c|ts)", "featureId":"f19", "field":"层数",
     "value":"3", "ts":"2026-11-14T15:40:00+08:00", "op":"set"},
    {"featureId":"f19", "field":"所属单位", "value":"体育部", "ts":"…", "op":"set"}
  ]
}
```
- `op`: `set` / `delete`（删值）/ `addField`（新增字段名）
- **只增量**，永远不覆盖别人的整行

### 10.2 服务端最小接口

```
POST /map/patches            提交补丁（幂等，按 id 去重）
GET  /map/patches?mapVersion=&since=<ts>   拉增量（客户端定期同步）
GET  /map/snapshot?mapVersion=             拉合并后的全量（内测后期）
```
轻量实现：Cloudflare Workers + D1/KV，或现成服务器上一个表 + 两个路由。单表即可：

```sql
map_patch(id TEXT PRIMARY KEY, map_version TEXT, feature_id TEXT,
          field TEXT, value TEXT, op TEXT, user_key TEXT, ts TEXT, reviewed INT DEFAULT 0)
```
索引 `(map_version, feature_id, field, ts)`。

### 10.3 合并与冲突

- 客户端合并顺序：**本地 edits.json（自己的）> 服务器补丁（按 ts 新的覆盖旧的）**
- 同一 `featureId+field` 多来源冲突：内测期**取最新 ts**，同时把冲突记录留在后台供人工看一眼
- **审核策略（建议）**：内测期「先本地立即可见」+ 后台 `reviewed=0` 队列，你或代理定期过一遍；
  脏数据只影响自己看，不会立刻污染所有人
- 拿到人工确认后再置 `reviewed=1`，才进 `snapshot`

### 10.4 隐私与合规（这条不能松）

- 上传的只有 `featureId + 字段 + 值 + 匿名 key`，**不含**学号/姓名/设备 ID/位置
- `userKey` 是本地随机生成的 UUID，设置页可「重置」，重置后与历史数据脱钩
- **首次上传前必须明确告知并给开关**（默认**关**，用户主动打开「帮助完善校园地图」才上传）
- 字段名白名单 + 值长度上限（如 ≤ 200 字）+ 简单脏词/注入过滤
- 不采集任何定位信息（v1 无定位）
- 文档里写清：上传的是「校园公共设施信息」，不是个人信息

### 10.5 零成本起步（**建议先做这个**）

在服务器就绪前，先用**导出/导入**跑内测闭环：

1. 内测用户在自己手机上标注 → 「导出标注」得到 `campus_annotated_<version>_<ts>.geojson` + `.csv`
2. 用户发给你 → 你跑 `tools/map/merge_edits.py`（待写）合并多份，冲突按 ts 取最新
3. 合并结果重新打进 `manifest`/`edits` 下发给所有人（或直接进下一版 asset）

**这条路零开发、零合规风险**，能立刻开始收集；服务器版等数据量起来再上。
App 端只要保证「导出」这一步做扎实（票 12 §7 已要求）。
