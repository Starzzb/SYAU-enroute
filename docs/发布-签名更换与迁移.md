## 2. 换钥之后能不能覆盖安装

**不能。** Android 在安装期先比对「已装包的签名」与「新包签名」，不一致直接拒绝，跟 versionCode 大小无关：

```
adb install -r app-release.apk
Failure [INSTALL_FAILED_UPDATE_INCOMPATIBLE: Package cn.dkarbon.enroute
signatures do not match previously installed version; ignoring!]
```

对应真机表现（华为 / 小米 / OPPO 都一样）：安装器弹「应用未安装」「更新包与已安装应用不兼容」，且**不会**自动帮你卸载。所以：

- **同包名 + 新签名 = 必须先卸载旧的**，没有例外；
- 卸载会清 `/data/data/cn.dkarbon.enroute`：课表缓存、地图标注、收藏、加密的登录凭据、偏好设置全部消失；
- 私钥无法从已发 APK 反推（APK 里只有证书公钥），git 历史里也从来没有过 release 密钥（只有 `debug.keystore`），所以**旧密钥确认无法找回**。

## 3. 现有更新通道能做什么、不能做什么

App 的更新链路（`data/UpdateCenter.kt` + `ui/settings/UpdateSection.kt`）：

```
GET releases/latest.json（5 条候选源）→ 比 versionCode → 弹窗 → 下载 APK → sha256 校验 → 交给系统安装器
```

- **能**：把 `latest.json` 的 `versionCode` 提到 320，m30 用户下次开 App 会收到「可更新到 0.7.4+m31」的弹窗，`notes` 里的一句话会显示在弹窗里 —— 这是唯一能主动触达老用户的渠道。
- **不能**：替用户卸载旧版。安装动作交给系统安装器，签名不匹配那一步我们插不进任何代码，只能事先在文案里讲清。
- **也不能**：让 m30 的弹窗显示长篇步骤（m30 的弹窗只有一行 `notes`）。所以 `notes` 必须一句话讲完最关键的指令，详细步骤放 GitHub Release 正文 + issue。

## 4. 迁移方案（推荐路径）

**一次性换钥，发布「断代版」**：

1. 新密钥生成到仓库外固定位置，例如 `O:\dev\keys\enroute-release-v2.jks`，别名 `enroute`：
   ```
   keytool -genkeypair -v -keystore O:\dev\keys\enroute-release-v2.jks ^
     -alias enroute -keyalg RSA -keysize 4096 -validity 10000 ^
     -dname "CN=SYAU Enroute, O=dkarbon, C=CN"
   ```
2. `local.properties` 的 `ENROUTE_STORE_FILE` 指向新文件（口令沿用或换新，四个键一起改）。
3. `versionCode` 跳到 **400** / `versionName` `0.8.0+m32`，让「断代」在号码上一眼可见，也拉开与 m31 的距离。
4. `latest.json` 的 `notes` 一句话：**「这一版换了签名，需先卸载旧版再装（先导出地图标注）」**。
5. GitHub Release 正文写「怎么少丢东西」：
   - 卸载前：地图 → 导出标注 → 另存 GeoJSON / CSV 到手机存储（这份文件卸载不受影响）；
   - 课表、成绩重登后自动重抓（内网）；
   - 收藏与偏好需重新设置（没有导出入口）；
   - 卸载 → 装新包 → 重新登录 → 地图里导入标注（若需要）。
6. `docs/版本控制与发版流程.md` §3 补两条：**密钥三处备份**（加密网盘 + 离线 U 盘 + 密码管理器附件）、**每次发版核对证书 SHA-256**（写进 Release 正文，出问题时能一眼看出是不是换过钥）。

## 5. 备选路径（按代价排序）

| 方案 | 代价 | 适用 |
|---|---|---|
| A 换钥 + 一次性卸载（上面第 4 节） | 每个用户丢一次本地缓存 | 默认，推荐 |
| B `adb uninstall -k` 保数据后装新包 | 只对有电脑 + adb 的用户有效，且不同 ROM 表现不一 | 少数玩家用户，写进 Release 附录即可 |
| C 换包名（`cn.dkarbon.enroute.next`）与旧版并存 | 用户手机里两个 App，长期要维护两套包名与更新通道 | 不推荐 |
| D 找回旧密钥 | 一旦找回就是零代价 | 已排除：全盘无 `.jks`，git 历史无 release 密钥 |

## 6. 长期纪律（写进 §3，随发版文档一起生效）

1. 密钥**绝不入库**，但必须有仓库外备份：加密压缩后放网盘 + 一份离线介质，口令放密码管理器。
2. `apksigner verify --print-certs` 的 SHA-256 每次发版记进 Release 正文与本文档 §1 表格。
3. 换机 / 重装系统后第一件事：`Test-Path O:\dev\keys\enroute-release.jks`，缺了就先找密钥再动代码。
4. 想让「签错」立即可见：CI 或 `build-release.bat` 里加一步校验 `apksigner verify` 的证书指纹，不等于预期值就红字退出（本次就是这样发现的）。
